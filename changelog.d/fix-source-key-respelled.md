- **Behaviour change: an incremental export reaching its server under another address is refused instead of re-reading the whole table.** The progress of an export is keyed by its source (`engine://host:port/database`), so a config that reached the same server as `localhost` after `127.0.0.1`, by an IP after a DNS name, or from a container or a scheduler after a cron job, found no cursor under the new key and exited 0 after delivering the whole table again beside the rows already delivered (0.32.2 and earlier, see #690). **Now** a run of an incremental, `keyset_incremental` or MongoDB `resume` export that holds no progress on its source, while another source of the same export holds a cursor that delivers to the same destination, stops before reading with `RIVET_STATE_CURSOR_SOURCE_RESPELLED` (exit 5); `rivet plan` refuses the same way. Two sources that deliver to their own destinations keep their own cursors and are not refused. A cursor written before state v33 records no destination and is not compared. **What to do:** if both addresses are one server, `rivet state accept -c <config> --export <name>` moves the progress (cursor and checkpoint rows) onto the address the config names and the next run continues from the cursor; if they are two servers sharing a destination, `rivet state accept` followed by `rivet state reset -c <config> --export <name>` starts the new address over with a full pass (empty the destination first if the pass lands in it), or give the export a destination of its own. State written before the upgrade is read as it is: nothing is migrated.
