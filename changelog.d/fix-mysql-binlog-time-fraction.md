- **A MySQL CDC row with a negative `TIME(1)` or `TIME(2)` value that has a fraction was decoded wrongly or crashed the run (TF-1).** The binlog decoder in `mysql_common` 0.37.3 subtracted from an unsigned fraction byte: a debug build panicked with `attempt to subtract with overflow`, and a release build wrapped to a duration of about 625 hours. The row of ANY table in the binlog could trigger it, captured or not, because rivet decodes every row event it reads. **Now** the build uses a patched `mysql_common` (the fix is submitted upstream as blackbeam/rust_mysql_common#200 and the patch is dropped once it is released), and `-00:00:00.50` is read as `-00:00:00.500000`. The fix ships in the release binaries and the Docker image; `cargo install rivet-cli` from crates.io builds against the unpatched `mysql_common` 0.37.3 (cargo drops `[patch]` when it packages a crate) and gets the fix only once upstream releases it. **What to do:** a stream or snapshot-plus-stream table with a `TIME(1)` or `TIME(2)` column that held negative values with a fraction before the upgrade may hold wrong text in a `string` column delivered by an earlier release; re-run its `initial: snapshot` leg (or a one-off `mode: full` export of the table) to replace those rows. Other TIME precisions and positive values were never affected.
