- **A CDC baseline leg whose text-declaration check could not run now says so.** On a PostgreSQL source, `rivet run`, `check` and `doctor` refuse a baseline leg that declares `text` under `columns:` over a date, time, timestamp or array column, because the change stream renders that cell in its own form (see the refusal added with the PostgreSQL text remedy). When rivet could not connect to the source, or the catalog describe failed, the check was skipped with no word. Now a WARN names the export, the step that failed (`connect` or `describe`), the credential-masked cause, and that the check did not run; the guard itself still refuses nothing and the exit code of the guard is unchanged. The WARN does not say whether the leg is admitted: `rivet check` and `doctor` on a source that cannot be connected still refuse a leg with `columns:` overrides as `RIVET_SOURCE_CONNECT_FAILED` (exit 2, `was not admitted`), and a describe that fails on a reachable source does not stop the leg. A leg whose `columns:` declare no `text` column draws no WARN even on an unreachable source, and a non-text override there is refused by the same `check` and `doctor` stop as before. When the caller already holds a source connection, the guard reads on it instead of opening a second one. A source that is reachable, a leg that declares no `text` column and a non-PostgreSQL source are unchanged and print nothing new. Nothing written before the upgrade changes. **What to do:** none for a WARN; restore the source connection and re-run `rivet check` to get the refusal where one applies.
