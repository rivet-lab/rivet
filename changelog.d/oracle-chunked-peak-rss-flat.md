- **A chunked export's peak memory no longer grows with the table on Linux x86_64, most visibly on Oracle.** Behaviour change. jemalloc, rivet's allocator, kept every freed page for 10 s before returning it to the operating system. A paged read frees a full page of row and Arrow buffers every few seconds, so the process kept pages from several pages at once and its peak resident memory rose with the number of pages read: an Oracle `mode: chunked` run of 5 million rows peaked up to 2.0 times a 1 million row run (171 to 220 MiB against 111 to 170 MiB on a hosted x86_64 runner), while the same run under a 250 ms return peaked 101 to 116 MiB at 5 million rows and 96 to 116 MiB at 1 million. **Now** the binary returns freed pages after 250 ms (`dirty_decay_ms:250`). Peak memory falls on every engine (5 million rows in `full` mode: MySQL 154 to 139 MiB, SQL Server 187 to 161 MiB, Oracle 181 to 166 MiB, PostgreSQL unchanged at 107 MiB) and a run takes up to 6 percent more CPU. Tables, state and output written before the upgrade are untouched. **What to do:** nothing; to keep jemalloc's own timing set `_RJEM_MALLOC_CONF=dirty_decay_ms:10000` in the environment, which still overrides the built-in value.
