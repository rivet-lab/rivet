- **A parallel keyset export over a skewed uuid key now balances its ranges by density (refs #1059, #1066).** Through the previous release the seek path recut ranges by density only for integer keys; a uuid key (a UUIDv7 or a uuid with a dense block and a gap above it) kept its key-space cuts, so one worker could read most of the table while the rest idled. **Now** a uuid key on PostgreSQL, MySQL and Oracle is probed and recut the same way: a heavy range is split where its density changes, a cut already passed by the previous snapped boundary is skipped instead of stacking one-row ranges, the recut keeps trying through three non-improving rounds and up to eight rounds so UUIDv7 bursts far apart in time end up in balanced ranges, and a probe over fewer than 200 rows counts them instead of estimating 200. The 10M-row catalog threshold no longer applies to such keys: an integer or uuid key takes the seek and recut path at any table size, so the start of the export no longer waits for a COUNT and OFFSET scan. Only a key with no axis (a string, a SQL Server `uniqueidentifier`, whose order differs from the byte order of the text) keeps exact row percentiles under 10M catalog rows. The run log names the path (`seek+recut`, rounds and ranges). Ranges and parts written by an earlier run are untouched: a resumed run reuses its stored boundaries. **What to do:** nothing; a uuid-keyed export under `parallel: N` may now run in more ranges than before, and the extra statements are index seeks bounded to 200 entries.
