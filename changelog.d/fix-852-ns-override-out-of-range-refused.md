- **A SQL Server `datetime2` or `datetime` value outside 1677-09-21..2262-04-11 under a `columns:` override of `timestamp_ns` was written as NULL, with exit 0.** Arrow holds a nanosecond timestamp in an `i64`, so a year-1600 or year-2300 value cannot be stored; the converter wrote NULL for it and the run reported success, so a second client read a missing value where the source held one (found 2026-11-06, see #852). **Behaviour change, changed stop:** such a value now refuses the run with `RIVET_SOURCE_VALUE_UNREPRESENTABLE` (exit 5, was exit 0 with NULLs) naming the column and the value, before any part is written. The same condition on an Oracle `timestamp_ns` / `timestamp_tz_ns` column was already a refusal but uncoded and exit 1 (`RIVET_SOURCE_OVERRIDE_WIRE_MISMATCH`); it now gives the same code and exit 5 as SQL Server, through one function. Values inside the range keep every digit (a `datetime2(7)` keeps its 100 ns tick); a real NULL stays NULL. **What to do:** declare the column `timestamp`, which keeps the full year range at microseconds, or remove the override; or CAST the column in the export's `query:`. Tables written before the upgrade are not changed: a Parquet file or warehouse table written from such a column under the override holds NULLs where the source held values, and is repaired by re-running the export with `timestamp` into a fresh destination (a `mode: full` run, or a `rivet state reset` of an incremental export).
