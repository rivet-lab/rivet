- **A SQL Server `datetime2`, `datetimeoffset`, `datetime` or `smalldatetime` column declared `text` (or `string`) under `columns:` is now delivered as the server's own text, for every year from 0001 to 9999.** Behaviour change. Before, the declaration was refused at plan time with `RIVET_SOURCE_OVERRIDE_WIRE_MISMATCH`, so a `datetime2(7)` or `datetimeoffset(7)` value outside 1677-09-21..2262-04-11, which the nanosecond default refuses with `RIVET_SOURCE_VALUE_UNREPRESENTABLE`, had no remedy that kept its seventh digit. **Now** the declaration is read and the column lands as `Utf8` holding `YYYY-MM-DD hh:mm:ss[.fraction]` at the type's scale (`datetimeoffset` adds ` +hh:mm`); the refusal for an out-of-range value names `<column>: text` as the first remedy. The `datetime2(7)` / `datetimeoffset(7)` default is unchanged: it stays `Timestamp(ns)` and still refuses a value outside the nanosecond range. Tables, state and exports written before the upgrade are untouched: no config that ran is read differently, and only a config that declared `text` over these types (refused before) now runs. **Unchanged stop:** a `mode: cdc` export whose pending baseline leg declares `text` over these types stays refused with `RIVET_SOURCE_OVERRIDE_WIRE_MISMATCH` (exit 1, before any row), because the change stream renders the same cell in its own form (a `datetime2(7)` as `.000000100`, a `datetimeoffset` shifted to UTC with the offset dropped, a `datetime` as `.996667`) and one `__changes` log would hold two spellings; the message names the column and says to remove it from `columns:`, after which the baseline and the stream both deliver the column's own type (for a `datetime2(7)` or `datetimeoffset(7)` that holds a value outside 1677-09-21..2262-04-11, the message names `timestamp` or `timestamp_tz` instead: microseconds over the full range, on the baseline and on the stream). A stream-only export and a baseline already written are unchanged: a stream-only export declared `text` delivers the change stream's rendering of the cell (a `datetime2(7)` with nine fraction digits, a `datetime` as `.996667`, a `datetimeoffset` shifted to UTC with the offset dropped), not the server's own text. **What to do:** to carry an out-of-range value as the server's own text in a batch export, add `columns: {<column>: text}` to the export (a stream-only CDC export takes the same declaration and receives the stream's rendering); for a `mode: cdc` export with a baseline, declare the column `timestamp` (or `timestamp_tz`) instead, which delivers the full range at microseconds on the baseline and the stream, and remove a `text` declaration only when the column holds no value outside the nanosecond range; to keep the previous behaviour, change nothing. The `RIVET_SOURCE_VALUE_UNREPRESENTABLE` (exit 5) text names the same split. **Also changed:** the `RIVET_SOURCE_VALUE_UNREPRESENTABLE` (exit 5) refusal of an Oracle nanosecond timestamp (`TIMESTAMP(7..9)`) value outside 1677-09-21..2262-04-11 now names `<column>: text` under `columns:` as a remedy, ahead of the `timestamp` / `timestamp_tz` declarations and the `query:` CAST it already named, and says nothing about SQL Server or a CDC baseline; the exit code and the code are unchanged. On a SQL Server `mode: cdc` baseline leg that declares `text` under `columns:`, a catalog that cannot be read (no connection, or the describe fails) no longer passes the check silently: a WARN names the export, the step that failed, the credential-masked cause and that the check did not run, the same as for PostgreSQL, and nothing is refused.
