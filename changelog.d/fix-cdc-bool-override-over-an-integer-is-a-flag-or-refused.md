- **A PostgreSQL, SQL Server or Oracle stream delivered every non-zero integer under a `bool` override as `true`; it is now refused.** Behaviour change. A `columns: { c: bool }` override over a PostgreSQL integer, a SQL Server `int` or an Oracle `NUMBER` column was read by a CDC run as `value != 0`, so 2, 5 or -1 became `true` with exit 0, where MySQL's stream and every batch export refuse a value outside 0 and 1. **Now** the stream refuses such a value on every engine `RIVET_SOURCE_VALUE_UNREPRESENTABLE` (exit 5) naming the column, the value and its row, before any part of that batch is written and before the checkpoint moves; 0, 1 and NULL are delivered as before, and a MySQL integer, `TINYINT(1)` or `BIT(1)` flag keeps its reading. Two MySQL readings change with it: a `BIT(n)` with n above 1 under a `bool` override now refuses a value other than 0 and 1 where it delivered `true`, and the value a refused signed `MEDIUMINT` names is the signed one (-1, not 16777215). Parts and tables written before the upgrade are untouched; rows a stream already delivered as `true` keep that value. **What to do:** declare the column `columns: { c: int64 }` to carry the number, or correct the values to 0 and 1; after a refusal, follow the re-baseline step it prints.
