- **`source.columns_from: grants` is now accepted on SQL Server, batch and CDC (behaviour change; closes #713, part of #711; supersedes #1050).** Through the previous release a SQL Server config carrying the key was refused at load with `RIVET_CONFIG_SOURCE_MODE_UNSUPPORTED`, and a login granted `SELECT` on some columns of a table (`GRANT SELECT ON dbo.t (id, name)`) was refused by the server at `SELECT *`. **Now** a SQL Server source with `columns_from: grants` delivers only the columns the server says the login may `SELECT` (`HAS_PERMS_BY_NAME(..., 'COLUMN')`): batch reads and the baseline snapshot select only them, and the change stream is read from a capture instance made of exactly them. SQL Server enforces the stream itself: the capture instance's change function returns nothing to a reader that may not `SELECT` every column it captures, so an instance that holds a column the login may not read, or leaves a readable one out, is refused with `RIVET_SOURCE_CDC_PREREQUISITE` (exit 1) naming the columns and the `sys.sp_cdc_enable_table ... @captured_column_list` statement that fixes it. An unreadable key, or no readable column, is refused with `RIVET_SOURCE_COLUMNS_UNREADABLE`. A grant change while a run is open is seen at the next batch read and refused with `RIVET_SOURCE_CDC_GRANTS_CHANGED` (exit 2) with nothing of that batch delivered. **What to do:** create an instance over the readable columns, point `cdc.capture_instance` at it, grant the login `SELECT ON SCHEMA::cdc`, and re-baseline the export with `cdc.initial: snapshot` (a checkpoint taken on the old, wider instance cannot resume on the new one and is refused as a log gap); verified by the `live_cdc_column_grants_mssql` cells. No state or table written before the upgrade changes: configs that carried the key were refused before, and configs without it read as they did.
