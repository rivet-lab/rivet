- **`rivet cdc --checkpoint` read and acked a checkpoint a `mode: cdc` export owns, and the export then skipped those changes.** `rivet run` records which stream owns a checkpoint (`<checkpoint>.owner`) and refuses a second one with `RIVET_SOURCE_CDC_CHECKPOINT_SHARED`; the `rivet cdc` command never looked at that record, so it continued from the export's position, advanced it (and on PostgreSQL acknowledged the slot), and exited 0 while the export's next run missed everything the command had read. **Now** `rivet cdc --checkpoint` claims its checkpoint through the same record before it dials the source, with the file present or deleted. **Changed stop (behaviour change):** `rivet cdc --checkpoint <file an export owns>` now exits 5 `RIVET_SOURCE_CDC_CHECKPOINT_SHARED` instead of reading; and a `mode: cdc` export is now refused (exit 5, same code) a checkpoint a `rivet cdc` command recorded, since the command now writes `<checkpoint>.owner` as `{"config":"","export":"rivet cdc"}`. **What to do:** give the command a `--checkpoint` of its own and keep the shared file, the export's position; if the command is finished and the export should continue from where it stopped, delete `<checkpoint>.owner` and run the export again. Checkpoints written before this version have no command record, so nothing is refused until the command runs with `--checkpoint` on this version; existing export owner records read unchanged.
