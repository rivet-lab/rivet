- **Behaviour change: `rivet state reset --export <name>` of a `partition_by` export now clears the progress of its partitions; before, it printed "State reset" and cleared nothing.** The cursor and progression of such an export are held per partition, under `<name>__<value>`; the reset looked for the declared name only, so the next run exited 0 with `_SUCCESS` and no parquet in every partition, and a destination emptied on the documented advice stayed empty with `validate` green. The refusals that print `rivet state reset --export <name>__2026-01-01` also ended in `RIVET_CLI_EXPORT_UNKNOWN`. **Now** a reset of the declared name clears the export's own rows and every stored partition's rows (cursor and progression) in one transaction and lists the partitions it cleared; a reset of one stored partition's name clears that partition only; a partition the state does not hold is refused with `RIVET_CLI_EXPORT_UNKNOWN`, naming the partitions it does hold. `rivet state show` and `rivet state progression` list the partitions of the declared exports, and `rivet state accept` on a partitioned export or one of its partitions is refused with `RIVET_STATE_ACCEPT_PARTITIONED`. This holds for an incremental export and for a chunked export with `partition_by` alike (the committed boundary of each partition goes with its cursor). The reset takes the run lease of the export and of every partition it clears: while a run holds one, it waits `--lock-wait` seconds (600 by default) and then stops with `RIVET_STATE_LOCK_TIMEOUT` (or at once with `RIVET_STATE_RUN_IN_PROGRESS` under `--lock-wait 0`), naming that export and clearing nothing; it needs no more open files for a family of 1000 partitions than for 10. Partitions stored under another spelling of the source (the default port dropped) go with the reset, and a partition that exists only for another source is neither listed nor cleared. A mode `full` export with `partition_by`, a plain export and an export declared under the name of a would-be partition (`events__x` beside `events`) are unchanged. **What to do:** cursors that partitions already hold from earlier runs are cleared by the first reset after the upgrade; nothing in state needs a step; a reset stopped by a live run is repeated once the run has ended. A reset made before the upgrade that cleared nothing is repeated once, with the destination emptied first if the full pass lands in it too.
