- **`rivet validate` exited 0 on a prefix whose delivery the state records and the destination no longer holds.** A prefix with no `manifest.json` and no `_SUCCESS` was read as a legacy run (`legacy_run`, exit 0) even when the state held a successful run of that export at exactly that destination, so a gate `rivet validate && deploy` passed over a delivery that had been removed or a destination that had moved. **Now** a batch export whose prefix holds neither file fails with `RIVET_VERIFY_DELIVERY_ABSENT` (exit 3) when `run_status` records a `success` run of that export at that destination, and the message names the remedy. **Behaviour change:** a state written before the upgrade counts, so `validate` can now exit 3 on a prefix that exited 0 before; it is the same prefix the earlier run delivered and the destination lost. A prefix never delivered (no `success` run of the export at that destination), a prefix with no state file (none is created), a `failed`, `interrupted` or `running` run, another export's run, another `{date}` and a CDC export are unchanged: `legacy_run`, exit 0. A state that cannot be read cannot prove a prefix was never delivered, so `validate` refuses with `RIVET_STATE_FILE_CORRUPT` instead of exiting 0, and only when the prefix holds no manifest. **What to do:** restore the prefix from a backup, or deliver it again with `rivet run --export <name>` (for an incremental or chunked export run `rivet state reset --export <name>` first, so the run starts over instead of continuing from its stored progress). A `{date}` prefix removed on purpose (a retention sweep) also exits 3 under `validate --date <that day>`, because the state still records its delivery; validate the days that are kept. A `_SUCCESS` without a manifest still fails (`RIVET_VERIFY_MANIFEST_MISSING`, exit 3), as before.
