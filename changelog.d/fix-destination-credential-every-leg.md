- **A destination's named credential signed the object-store write only; the BigQuery load, its pin and the compaction ran as the ambient identity, and an S3 `aws_profile` beside env keys ignored the keys.** With `credentials_file:` naming a service-account key, every BigQuery request of `rivet load` still carried the token of the ambient ADC identity (the gcloud user), so the load wrote with an identity the config never named. An S3 destination naming `aws_profile` beside `access_key_env`/`secret_key_env` signed with the profile alone and `rivet check` exited 0. **Now** one reader of the destination's credential fields (`DestinationCredential`) serves the object-store write, the config check and the BigQuery load: the load signs as the named service-account key. **Behaviour change, three new stops:** (1) `aws_profile` beside `access_key_env`, `secret_key_env` or `session_token_env` is refused when the config loads with `RIVET_CONFIG_DESTINATION_AUTH_INVALID` (exit 1); (2) `RIVET_BQ_ACCESS_TOKEN` set beside a named `credentials_file:` is refused with the same code; (3) a named key that is not a `service_account` key (an `impersonated_service_account` or `external_account` file) stops a BigQuery load with `RIVET_DEST_CREDENTIALS_INVALID`, where the load used to run as ADC. **What to do:** for (1) remove `aws_profile` to sign with the env keys, or remove the env key fields to sign with the profile; for (2) unset `RIVET_BQ_ACCESS_TOKEN` to load as the key, or remove `credentials_file:` to load with the token; for (3) point `credentials_file:` at a service-account key, or remove it to load with ADC. A load that ran before the upgrade as the ambient identity wrote its tables under that identity; no state or table is rewritten, so give the named service account the BigQuery permissions the load needs before the first load after the upgrade.
