- **Two sources on different hosts shared one state key when their URL held an `@` after the host.** `postgresql://h1:5432/a?application_name=svc@corp` and the same URL on `h2` both keyed as `postgres://corp:5432`, so they shared one run lease, one resume progress and one load spec; on SQL Server the host was read from the query text. **Now** every reader of a connection URL (state key, run lease, host:port in errors, the SQL Server and Oracle parsers, the redactors and the plaintext-password warning) reads the userinfo and host from the authority only, the text up to the first `/`, `?` or `#`, through one reader in `url_text`. A URL with no `@` after the authority keeps the key it had. **Behaviour change:** an export that ran under the old key (`postgres://corp:5432` above) is refused on its first run after the upgrade with `RIVET_STATE_CURSOR_SOURCE_RESPELLED` (exit 5), nothing read or written. **What to do:** `rivet state accept -c <config> --export <name>` moves the progress to the new key and the next run continues from the same cursor (verified on PostgreSQL: the old binary wrote the cursor, the new one refused, `state accept`, the next run delivered only the new rows). Two servers that shared the old key: `rivet state accept` followed by `rivet state reset`. Also a SQL Server URL whose password holds a raw `/`, `?` or `#` is now refused with `mssql url missing user@host`: percent-encode the password (`%2F`, `%3F`, `%23`), as rivet-built URLs already do.
