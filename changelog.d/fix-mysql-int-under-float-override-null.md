- **Behaviour change: a MySQL `columns:` override that the column's values do not fit now stops the run instead of writing NULL for every row.** An integer column (or primary key) declared `float4` or `float8` was delivered as all NULL: `check` exit 0, `run` exit 0, status success, type report `exact`. The same fallthrough wrote NULL for any value of a kind the declared type does not read (for example a `DOUBLE` under `int8`, a `TIME` under `text`). **Now** an integer under `float4`/`float8` is delivered with its values while the float holds it exactly (up to 2^24 and 2^53), and past that the run stops with `RIVET_SOURCE_VALUE_UNREPRESENTABLE` (exit 5); any other value the declared type cannot read stops with `RIVET_SOURCE_OVERRIDE_WIRE_MISMATCH` (exit 1). Text that does not parse as the declared type is still NULL, as before. **What to do:** a run that now stops names the column and the remedy: declare `float8` or `decimal(20,0)`, remove the override, or `CAST` the column in the export's `query:`. Files written before the upgrade keep their NULLs and are not repaired: re-export an affected column after the upgrade.
