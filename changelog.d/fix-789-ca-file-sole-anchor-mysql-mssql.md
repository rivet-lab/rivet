- **Behaviour change: on MySQL and SQL Server, `tls.ca_file` trusted the system store as well as the file (#789).** With `mode: verify-ca` or `verify-full` and a `ca_file`, a server certificate signed by any CA the operating system trusts was accepted, so a config that pinned a private CA still connected to a server holding a public certificate (under `verify-ca` the host name is not checked, so any public certificate passed). **Now** the `ca_file` CA is the only trust anchor on MySQL and SQL Server as on Postgres and MongoDB, and a certificate it did not sign is refused with the TLS handshake error. The release binaries and the Docker image build against patched `mysql`, `tiberius` and `opentls` drivers (forks under rivet-lab, pinned by commit); `cargo install rivet-cli` from crates.io drops the `[patch]` and still trusts the system store beside `ca_file` on these two engines. **What to do:** a MySQL or SQL Server source whose server certificate was signed by a CA other than the one in `ca_file` stops connecting; name the CA that signed it in `ca_file` (MySQL accepts several certificates in one PEM file, SQL Server too), or drop `ca_file` to let the system store decide. Both were verified by the offline cells in `tests/offline/tls_ca_file_sole_anchor.rs`.
