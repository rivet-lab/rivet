- **Behaviour change: a MongoDB change log loaded into BigQuery or Snowflake is now ranked by the numeric clusterTime `ct`, then the numeric ordinal `ord`, then the resume token, instead of by the resume token alone.** The resume token is an internal MongoDB format, not a contract, and ClickHouse already ordered by `(ct, ord)`; now all three warehouses agree. The current-state view and `rivet compact` (the BigQuery MERGE and the Snowflake DELETE+INSERT) use the one order. The two columns are read as `NUMERIC` (BigQuery) and `NUMBER(38,0)` (Snowflake), which hold a clusterTime up to 2^64-1, and compared as numbers (ordinal 10 outranks 9). **What to do:** nothing for a log that is new or that already holds `ct` and `ord`; the view text changes and a `CREATE OR REPLACE VIEW` on the next load applies it. A `<table>__changes` written by a rivet older than the `ct` stamp keeps working with no refusal: its rows carry no `ct`, rank below every stamped row, and rank among themselves by the resume token as before. Snapshot rows carry `ct = 0, ord = 0`, so they rank below every change, as they did on ClickHouse. One consequence: a stateless load (no state database) that re-snapshots into a `<table>__changes` which already holds changes of the same key now ranks the new snapshot row below those older changes, where the resume token used to rank it above them; a stateful load and the base+buffer layout already refuse that re-baseline, and for a stateless load the remedy is to truncate `<table>__changes` before re-baselining.
