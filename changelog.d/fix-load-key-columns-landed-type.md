- **Behaviour change: an incremental load whose cursor lands as text, or whose primary-key column lands finer-collapsed, is now refused (exit 5) instead of loading a wrong current-state view with exit 0.** A bare Oracle `NUMBER` cursor lands as text, which a warehouse orders as `99` after `100`, so a row updated across a digit boundary kept its stale version in the view; a SQL Server `datetime2(7)` primary-key column lands at microseconds, so two rows that differ only below a microsecond became one row of the view. **Now** `rivet load`, `rivet compact` and `rivet check` stop with `RIVET_LOAD_KEY_COLUMN_LANDS_INEXACT` (exit 5, that table only) before any warehouse statement, naming the column, its source type and the remedy; no delivered byte changes. **What to do:** declare the column under the export's `columns:` (`VER: int64` or `decimal(p,s)` for the cursor, `timestamp_ns` / `timestamp_tz_ns` for the key, or cast it in the export's `query:`), run the export again and reload; for the key column run `rivet state reset --export <name>` before that run, because parts already extracted hold microseconds (verified on SQL Server into ClickHouse: declaring `timestamp_ns` and running on kept one view row, with the reset both rows). A table already loaded keeps its column type: drop its change log and its view and run `rivet state reset --export <name>` before the run (verified on Oracle into ClickHouse: the old binary left `2 | 99` after `99 -> 100`; the branch refuses, and after the drop, reset and rerun the view holds `2 | 100`, then `2 | 101` after the next update). A spec recorded by `rivet run` before this upgrade does not carry the sub-microsecond fact: run the export once more before the first `rivet load` for the SQL Server key check to see it (`rivet check` reads the source and needs no run). `rivet run` itself is not refused: the stop lands at the load.
