- **Behaviour change: the planner now accepts a keyset key only when the reader can advance it, on every engine and for every key shape.**
  Before, the check was a list of type names kept apart in each engine's catalog probe, and it did not match what the cursor can read and re-bind. A MySQL table with no integer primary key whose only unique key was `BINARY(16)`, `TINYINT(1)`, `TIME` or an `ENUM` was keyset-paged by that key by itself: one page ran as a snapshot with exit 0, more pages stopped with exit 5 after the first page was written. A SQL Server `datetime2`/`datetimeoffset` key with more than 6 fractional digits (a bare `datetime2` is `datetime2(7)`) under `chunk_by_key:` read microseconds from a column of 100 ns ticks: where the data held fractions finer than a microsecond and `chunk_size` was 2 or more, it delivered duplicate rows with exit 0; where every value was a whole number of microseconds, main exported correctly. A composite `chunk_by_key:` accepted the same sub-microsecond and `ENUM` columns.
  **Now** one function (`keyset_key_refusal` in `src/source/keyset_key.rs`) decides from the delivered type, the planner and the composite check both call it, and it runs at plan time, so a table that fits in one chunk is refused as well. The refusal names the column and the cause and ends with the remedy. A decimal key keeps its refusal and the message now names the cause too; the decimal probes of PostgreSQL, MySQL and SQL Server no longer hide the column, so the planner states the cause instead of "no safe shape". `rivet init` calls the same function: it reads the types the server delivers for the table (`SELECT * ... LIMIT 0` through the engine's own type probe, the call the planner makes) and no longer keeps a type list of its own, so it scaffolds a keyset key exactly when the planner would accept it, on PostgreSQL, MySQL, SQL Server and Oracle. A `datetime2`/`datetimeoffset` with more than 6 fractional digits (SQL Server, a bare `datetime2` included) or a `TINYINT(1)` (MySQL) is no longer scaffolded as a keyset key. **Oracle:** the seam now also decides what the catalog filter and init's list decided (scaled `NUMBER`, binary floats, `TIMESTAMP WITH [LOCAL] TIME ZONE` and `TIMESTAMP(7..9)` stay refused, now with the seam's cause); a `FLOAT` column and an integer `NUMBER` with a negative scale are now admitted as keyset keys (not verified against a live Oracle). `init` reads the delivered types of each table it scaffolds; a table whose types cannot be read (no `SELECT`, a broken view) is scaffolded as before but never with a keyset key, and a schema scan prints `rivet: WARN [RIVET_INIT_TABLE_UNREADABLE] ...` naming the table, the cause and the remedy (grant `SELECT` on the table or leave it out of `init`); the scan goes on with the other tables. Existing configs and state are unchanged.
  **Changed stops:** MySQL, no integer primary key, auto-picked unique key of type binary, boolean, time, JSON or `ENUM`/`SET` (was exit 0 as a snapshot on one chunk, exit 5 after a partial write on many) now ends `RIVET_PLAN_CHUNK_KEY_UNUSABLE` (exit 1) at plan, check and run; SQL Server `chunk_by_key:` on a `datetime2`/`datetimeoffset` with more than 6 fractional digits, a bare `datetime2` (precision 7) included (was exit 0: duplicate rows when the data holds fractions finer than a microsecond and `chunk_size` is 2 or more, correct rows when every value is a whole number of microseconds) now ends `RIVET_PLAN_CHUNK_KEY_UNUSABLE` (exit 1) even when the data would have exported correctly; `rivet init --table T` on a table the init user cannot `SELECT`, and `rivet init` over a schema in which the init user can `SELECT` none of the tables found (was scaffolded or skipped), now end `RIVET_INIT_TABLE_UNREADABLE` (exit 1); a schema scan with at least one readable table does not stop for an unreadable one: main scaffolded or skipped it, this release does the same with the warning and never offers a keyset key for it; a composite `chunk_by_key:` that names such a column ends `RIVET_PLAN_CHUNK_KEY_UNUSABLE` (exit 1).
  **What to do:** key on an integer, text, uuid, date or timestamp column; for a SQL Server `datetime2(7)` or `datetimeoffset(7)` key declare `columns: {col: timestamp_ns}` (`timestamp_tz_ns` for `datetimeoffset`) so the cursor carries 9 digits, or change the key to a `datetime2(6)` column, an integer key, or run `mode: full`; or range-chunk an integer `chunk_column:`. **BigQuery:** `timestamp_ns` lands as `INT64` there (BigQuery `TIMESTAMP` is microsecond, see `docs/type-mapping.md` known gap 4), so for a native `TIMESTAMP` column use the other remedies. Every other key the reader advanced before keeps its plan, pages and files unchanged; a `datetime2`/`datetimeoffset` key with more than 6 fractional digits does not, it is refused as above. A plan sealed before the upgrade is not re-checked at apply: re-seal it with `rivet plan`.
