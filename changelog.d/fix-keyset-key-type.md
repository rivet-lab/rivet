- **Behaviour change: the planner now accepts a keyset key only when the reader can advance it, on every engine and for every key shape.**
  Before, the check was a list of type names kept apart in each engine's catalog probe, and it did not match what the cursor can read and re-bind. A MySQL table with no integer primary key whose only unique key was `BINARY(16)`, `TINYINT(1)`, `TIME` or an `ENUM` was keyset-paged by that key by itself: one page ran as a snapshot with exit 0, more pages stopped with exit 5 after the first page was written. A SQL Server `datetime2`/`datetimeoffset` key with more than 6 fractional digits (a bare `datetime2` is `datetime2(7)`; a column declared through an alias type such as `CREATE TYPE ts7 FROM datetime2(7)` included) under `chunk_by_key:` read microseconds from a column of 100 ns ticks: where the data held fractions finer than a microsecond and `chunk_size` was 2 or more, it delivered duplicate rows with exit 0; where every value was a whole number of microseconds, main exported correctly. A composite `chunk_by_key:` accepted the same sub-microsecond and `ENUM` columns; an Oracle composite key whose second column was a `TIMESTAMP(7..9)` paged on microseconds and delivered duplicate rows with exit 0 (53 rows for 40 distinct ids in the live probe).
  **Now** one function (`keyset_key_refusal` in `src/source/keyset_key.rs`) decides from the delivered type, the planner and the composite check both call it, and it runs at plan time, so a table that fits in one chunk is refused as well. The refusal names the column and the cause and ends with the remedy. A decimal key keeps its refusal and the message now names the cause too; the decimal probes of PostgreSQL, MySQL and SQL Server no longer hide the column, so the planner states the cause instead of "no safe shape". `rivet init` calls the same function: it reads the types the server delivers for the table (`SELECT * ... LIMIT 0` through the engine's own type probe, the call the planner makes) and no longer keeps a type list of its own, so it scaffolds a keyset key exactly when the planner would accept it, on PostgreSQL, MySQL, SQL Server and Oracle. A `datetime2`/`datetimeoffset` with more than 6 fractional digits (SQL Server, a bare `datetime2` and an alias type over one included) or a `TINYINT(1)` (MySQL) is no longer scaffolded as a keyset key. **Oracle:** a bare `NUMBER` (no precision or scale, delivered as exact text), `NUMBER(*,0)` and an integer `NUMBER(p)` key a seek, as on main: the one Oracle exemption in the seam lets a `NUMBER` delivered as `decimal_plain` text key a seek, and the cursor binds the text back through the column's own NUMBER comparison. The Oracle catalog probe reads the declared precision, scale and fractional-second digits of the table (`declared_wider_columns`) and hands the seam a typed fact (`Wider::FinerTimestamp` or `Wider::InexactNumber`); the seam applies it before it looks at the type `columns:` delivers, so a `columns:` override cannot lift it. A single-column key on a `NUMBER` with a scale (`NUMBER(12,2)`, `NUMBER(*,2)`, a negative scale such as `NUMBER(5,-2)` or `NUMBER(38,-5)`, `NUMBER(38,39)`) or on a `FLOAT` stays refused with the seam's cause, with or without a `columns: {K: int64}` or `{K: string}` override (main refused all of these; an earlier build of this change admitted them under an override and `NUMBER(12,2)` with fractions then failed uncoded in the run). A key on a `TIMESTAMP(7..9)` is refused on Oracle in a single or composite key, with or without `columns: {K: timestamp_ns}`; on Oracle that override does not help, because the reader delivers the column at microsecond precision for a cursor. A composite key whose second column is a `FLOAT` or a `NUMBER` with a scale still keys a seek exactly as on main (probed against main: 40 of 40 ids for a `FLOAT` in three value shapes, for a `NUMBER(12,2)` of whole numbers under an `int64` override or of fractions under a `string` override, and for a `NUMBER(5,-2)` under `int64`; a `NUMBER(12,2)` or `NUMBER(*,2)` holding fractions under an `int64` override fails in the run on main and still does; a `NUMBER(12,2)` of fractions without an override is refused on main and still is). `TIMESTAMP WITH [LOCAL] TIME ZONE` and binary floats stay refused as on main. PostgreSQL `jsonb` keeps keying a seek, single and composite, as on main (probed: 8 value shapes, 40 of 40 ids each, byte-equal exit and ids on main and on this branch). `init` reads the delivered types of each table it scaffolds; in a schema scan, a table whose types cannot be read (no `SELECT`, a broken view) is scaffolded as before but never with a keyset key (`rivet init --table T` on such a table stops, see Changed stops), and the scan prints `rivet: WARN [RIVET_INIT_TABLE_UNREADABLE] ...` naming the table, the cause and the remedy (grant `SELECT` on the table or leave it out of `init`); the scan goes on with the other tables. Existing configs and state are unchanged, except for the stops listed next.
  **Changed stops:** MySQL, no integer primary key, auto-picked unique key of type binary, boolean, time, JSON or `ENUM`/`SET` (was exit 0 as a snapshot on one chunk, exit 5 after a partial write on many) now ends `RIVET_PLAN_CHUNK_KEY_UNUSABLE` (exit 1) at plan, check and run; the same for an explicit single-column `chunk_by_key:` on a MySQL `BINARY(16)`, `TINYINT(1)`, `TIME` or `ENUM`, a PostgreSQL `bytea`, `time` or `boolean`, and a SQL Server `varbinary`, `time` or `bit` (main: `check` exit 0 and the run exit 5 `RIVET_SOURCE_PROBE_UNREADABLE` after 4 of 10 rows, for `ENUM` and `bit` exit 0 or a `check` error; verified live), and for a composite `chunk_by_key:` over a MySQL `ENUM` or a SQL Server `datetime2(7)` (main: exit 0); an Oracle composite `chunk_by_key:` whose second column is a `TIMESTAMP(7..9)` (was exit 0 with duplicate rows, now exit 1 at plan, `check` and run); an Oracle single-column `TIMESTAMP(9)` key with `columns: {K: timestamp_ns}` is unchanged (exit 1 on main and now, with a message that no longer promises the override helps); SQL Server `chunk_by_key:` on a `datetime2`/`datetimeoffset` with more than 6 fractional digits, a bare `datetime2` (precision 7) or an alias type over one included (was exit 0: duplicate rows when the data holds fractions finer than a microsecond and `chunk_size` is 2 or more, correct rows when every value is a whole number of microseconds) now ends `RIVET_PLAN_CHUNK_KEY_UNUSABLE` (exit 1) even when the data would have exported correctly; `rivet init --table T` on a table the init user cannot `SELECT`, and `rivet init` over a schema in which the init user can `SELECT` none of the tables found (was scaffolded or skipped), now end `RIVET_INIT_TABLE_UNREADABLE` (exit 1); a schema scan with at least one readable table does not stop for an unreadable one: main scaffolded or skipped it, this release does the same with the warning and never offers a keyset key for it; a composite `chunk_by_key:` that names such a column ends `RIVET_PLAN_CHUNK_KEY_UNUSABLE` (exit 1). The text of the `RIVET_PLAN_CHUNK_KEY_UNUSABLE` stop for an explicit `chunk_by_key:` that is not a usable keyset key is reworded (same code, same exit 1): the sentence about `decimal`/`numeric` keys is replaced by the cause of the named column (`Column 'k' is a decimal, which the cursor cannot advance past exactly.`) and one remedy line, and the "no safe shape" stop lists each unique key refused with its cause; match on the code, not on the words.
  **What to do:** key on an integer, text, uuid, date or timestamp column; on Oracle key on a `TIMESTAMP(6)`, a whole-number `NUMBER` or a text column (no `columns:` override lifts the refusal of a `TIMESTAMP(7..9)`, a scaled `NUMBER` or a `FLOAT`); for a SQL Server `datetime2(7)` or `datetimeoffset(7)` key declare `columns: {col: timestamp_ns}` (`timestamp_tz_ns` for `datetimeoffset`) so the cursor carries 9 digits, or change the key to a `datetime2(6)` column, an integer key, or run `mode: full`; or range-chunk an integer `chunk_column:`. **BigQuery:** `timestamp_ns` lands as `INT64` there (BigQuery `TIMESTAMP` is microsecond, see `docs/type-mapping.md` known gap 4), so for a native `TIMESTAMP` column use the other remedies. Every key not named under Changed stops keeps its plan, pages and files unchanged (probed against main on 61 shapes of PostgreSQL, MySQL and SQL Server and 28 of Oracle: same exit, same code, same delivered ids). A plan sealed before the upgrade is not re-checked at apply: re-seal it with `rivet plan`.
