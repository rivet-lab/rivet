- **Behaviour change: on Postgres, `tls.ca_file` trusted the system store as well as the file (#789).** With `mode: verify-ca` or `verify-full` and a `ca_file`, a server certificate signed by any CA the operating system trusts was accepted, although libpq with `sslrootcert` trusts only that file; a config could pin a private CA and still connect to a server holding a public certificate. **Now** the `ca_file` CA is the only trust anchor on Postgres, and a certificate it did not sign is refused with the TLS handshake error. MongoDB already behaved this way. **What to do:** a Postgres source whose server certificate was signed by a CA other than the one in `ca_file` stops connecting; name the CA that signed it in `ca_file` (one certificate per file), or drop `ca_file` to let the system store decide. **Still open:** MySQL and SQL Server trust `ca_file` beside the system store, because their drivers expose no sole-anchor option; the field doc and `docs/reference/config.md` say so.
