- **`rivet load` into ClickHouse refuses a part holding a `DATE` outside 1900-01-01 to 2299-12-31, before inserting anything.** Behaviour change. Before, the load read the footer of a timestamp column only, so a `Date32` column was never checked: the date 2300-01-01 (PostgreSQL, MySQL, SQL Server `DATE`) was stored by ClickHouse as 2299-12-31, silently, and any other date outside the range (`0001-01-01`, `9999-12-31`, `1899-12-31`, a PostgreSQL BC date) was refused by ClickHouse as `RIVET_LOAD_WAREHOUSE_REJECTED`. **Now** a part, pushed or pulled through a named collection, whose `Date32` column holds a value outside the range, or whose footer has no min/max statistics for it, is refused by rivet with `RIVET_LOAD_VALUE_OUT_OF_TARGET_RANGE` (exit 5, a refusal) naming the column and the value, as for a timestamp; nothing is inserted. A script that matched `RIVET_LOAD_WAREHOUSE_REJECTED` (environment, retried by cause) for such a date must match the new code. `rivet check` now grades a ClickHouse `Date32` column `warn` with the range, as it does a timestamp. A table loaded before the upgrade is not touched: a 2300-01-01 it already holds as 2299-12-31 stays so, and no new load of the same data succeeds. **What to do:** declare the column as `String` in the export's `columns:` to keep the value, or correct it at the source; to check a table loaded earlier, count the source rows `>= '2300-01-01'` against the table's `2299-12-31` rows.
