- **Behaviour change: on SQL Server a text key holding a non-ASCII value lost or repeated rows at a page boundary, exit 0.** A boundary literal was typed from the value (`N'...'` for non-ASCII), so a `varchar` key was ordered by the column collation but seeked in Unicode rules (`k > N'é''z'` skips rows the `ORDER BY` puts after it). It hit `chunk_by_key` (sequential and parallel), `mode: incremental` on a text cursor, `keyset_incremental` and `--split`. **Now** a non-ASCII boundary is rendered as `ISNULL((SELECT TOP 1 <key> FROM (<query>) WHERE 1 = 0), N'...')`, so the server converts it to the key's own type, code page and collation; an ASCII boundary and every other engine render the same SQL as before. A stored cursor longer than a since-narrowed column is cut to the column length. **What to do:** nothing for new runs; re-run an export that delivered a SQL Server text key with non-ASCII values through `chunk_by_key`, a text `cursor_column` or `--split` with `rivet state reset -c <config> -e <export>` followed by a run, because earlier parts may lack rows.
