- **Behaviour change: `rivet load` of an incremental or `cdc` export whose source has a column named `__op`, `__pos`, `__seq` or `__is_deleted` is now refused with `RIVET_LOAD_RESERVED_COLUMN` (exit 1), on every load target and for `rivet compact`.** Until now the refusal was raised only when the load had no recorded run to type its columns from; the normal first load after a `rivet run` was typed from that run and loaded without it. The column then collided with rivet's own change-log columns: a source `__is_deleted` switched soft-delete on for rows the source controls, and a source `__op` lost its values in the merge, so rows could vanish from a base table after `rivet compact` (seen on Snowflake and BigQuery; BigQuery could also stop after its base was renamed to `<table>__changes`). **Now** the load stops before the first warehouse statement, on every attempt, and names the column. **What to do:** rename or exclude the column in the export's `query:`, or load the table with `mode: full`, where rivet builds no such columns (a source column called `__is_deleted` must be a boolean on Snowflake). A table loaded before this release from such an export may already have lost rows: reload it with `mode: full` or from a renamed column; nothing is read from or written to the warehouse by the refusal itself, and state written before the upgrade is not changed.
