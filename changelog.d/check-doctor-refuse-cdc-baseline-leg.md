- **`rivet check` and `doctor` refuse a `mode: cdc` export whose first baseline run would be refused, before any row is read.** Behaviour change. The first `rivet run` of a CDC export with `initial: snapshot` (or `backfill:`) writes its baseline through a batch leg. Before, `check` and `doctor` exited 0 over an export whose baseline leg that run then refused: a column the export's `format:` cannot write (a `format: csv` export of a column typed `decimal(39..76, s)`, a nanosecond timestamp or a list: `RIVET_CONFIG_FORMAT_COLUMN_UNSUPPORTED`, exit 1), a column no Arrow type carries and no `columns:` entry declares (`RIVET_TYPE_UNSAFE_MAPPING`, exit 1), and a `columns:` override the source reader cannot build (`RIVET_SOURCE_OVERRIDE_WIRE_MISMATCH`, exit 1). **Now** `check` (with and without `--type-report`) and `doctor` stop at the same point with the same code while the baseline is pending, that is while the destination's `snapshot/_SUCCESS` marker is absent. `check` never opens the state database; once the marker is present the baseline is done and is not admitted again, so an export that already ran its baseline is not refused. `rivet plan` does not plan a CDC export and is unchanged. A refusal `run` raises only after it has read rows (`RIVET_SOURCE_VALUE_UNREPRESENTABLE`) or from the stream's own prerequisites (`RIVET_SOURCE_CDC_PREREQUISITE`) is unchanged. Files, state and tables written before the upgrade are untouched: a config `run` already refused is now refused earlier by `check` and `doctor`, and a config `run` ran is not refused. One divergence: when the state database records the baseline done but its `snapshot/_SUCCESS` marker is gone, `run` skips the baseline and `check` admits it again; restore the marker or run `rivet run` once. **What to do:** switch the export to `format: parquet`, or cast or drop the column in the query, or declare a type the reader can build under `columns:`.
