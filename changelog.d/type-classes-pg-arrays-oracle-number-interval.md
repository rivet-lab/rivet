- **A PostgreSQL `json[]`, `jsonb[]`, `interval[]`, `oid[]` or enum array column now delivers; an Oracle `NUMBER` or `FLOAT` of infinity and an Oracle `INTERVAL DAY TO SECOND` with a sub-microsecond fraction now stop the run with `RIVET_SOURCE_VALUE_UNREPRESENTABLE` (exit 5) instead of writing a changed value (behaviour change).** Through the previous release a one-dimensional array of those PostgreSQL element types was refused with the message that blames multi-dimensional arrays, so the column could not be exported; it is now delivered as a list of the element texts (`json`/`jsonb` as JSON text, `interval` as an ISO 8601 duration, enum as its label, `oid` as an unsigned `Int64`), and a genuine multi-dimensional array is still refused with the same message. Through the previous release an Oracle `NUMBER` or `FLOAT` holding infinity (what `FLOAT` arithmetic that overflows 9.99E125 stores) was delivered as the finite number `1E125` with exit 0, and an `INTERVAL DAY TO SECOND(7..9)` value was written at microseconds with a per-column warning; both now refuse the run, naming the column. An exact `1E125` is refused too, because the client prints it with the same bytes as infinity. Nothing written before the upgrade changes: a part already delivered keeps its values, so re-export a table whose Oracle `FLOAT` or `INTERVAL` column held such values. The remedy for a refused column (verified on Oracle 23ai Free): select `TO_CHAR(col) AS col` in the export query, which delivers the server's own text (infinity prints as `~`, an interval as `+000000001 02:03:04.000000005`); a column without such values, and an interval that holds only microseconds, export as before. A run that used to exit 0 on a `FLOAT` or `INTERVAL DAY TO SECOND(7..9)` column holding these values now exits 5, and the interval's warning (`fidelity=lossy`) is gone, as the mapping no longer loses digits.
