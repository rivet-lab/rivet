- **A GCS `credentials_file` that is no usable key fell back to the machine's own identity.** A `credentials_file` naming a directory, an empty file, malformed JSON or a JSON that is no service-account key passed config; the GCS store then dropped the named key and used the VM metadata identity or the ambient Google credentials, so on GCE or GKE the run wrote under an identity the operator did not choose, and elsewhere `validate` failed with a `metadata.google.internal` line. A relative `credentials_file` was also read under the working directory, so one config passed from one directory and failed from another. **Behaviour change.** **Now** the file is read once, beside the config for a relative path, and a directory, an unreadable, empty or malformed file, or a JSON that is no service_account, impersonated_service_account or external_account key stops the load with `RIVET_DEST_CREDENTIALS_INVALID` naming the field and the path; the store never reaches another identity. A missing file stays `RIVET_CONFIG_SECRET_UNSET`. **Changed stop:** an `authorized_user` file from `gcloud auth application-default login` named as `credentials_file` used to be ignored in favour of the ambient identity and is now refused; a relative `credentials_file` that only the working directory holds is refused naming both places. **What to do:** point `credentials_file` at a service-account key JSON, or remove the field to use the ambient Google credentials; move the key beside the config or make the path absolute.
