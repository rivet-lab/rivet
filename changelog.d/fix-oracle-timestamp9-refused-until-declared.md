- **An Oracle `TIMESTAMP(7..9)` column was delivered at microseconds, the sub-microsecond digits dropped, with a warning and exit 0.** A second client reading the target saw a different value than the source held, and nothing stopped the run. **Behaviour change, changed stop:** an undeclared `TIMESTAMP(7)`, `TIMESTAMP(8)` or `TIMESTAMP(9)` column, zoned or not, now refuses the run, `rivet check --type-report` and the change-data-capture run with `RIVET_TYPE_UNSAFE_MAPPING` (exit 1), with or without `--strict`, before any part is written. **What to do:** declare the column in the export's `columns:`. `timestamp_ns` / `timestamp_tz_ns` keep all nine digits (range 1677-09-21..2262-04-11); `timestamp` / `timestamp_tz` read microseconds, the old delivery, the same values. A change-data-capture export reads microseconds only, so there `timestamp` is the remedy. Tables written before the upgrade are untouched; a config that declares the column delivers exactly what it did.
