- **A MongoDB export whose collection was dropped, or dropped and created again, while it ran ended exit 0 with a `_SUCCESS` marker over the documents read so far.** The collection was checked once, with `listCollections`, and then read with `find`; a `find` on a collection dropped in between returns no documents and no error, the keyset runner reads an empty page as the end of the collection, and a collection created again in between was read as the old one. A keyset, full-scan or parallel `_id`-range run therefore finished clean with the pages it had, and a full load then replaced the warehouse table with them. **Now** the collection is listed before and after every read, its UUID is pinned at the first listing (a parallel run pins it before it samples the `_id` ranges and hands it to every worker), and a collection that is gone or listed under another UUID is refused. **Changed stop:** a run whose collection is dropped, or dropped and created again, while it reads ends `RIVET_SOURCE_COLLECTION_NOT_FOUND` (exit 1) instead of exit 0, and writes no `_SUCCESS`. **What to do:** create the collection again with its documents and run again; state and files written before the upgrade are untouched, the check adds `listCollections` calls only. **Behaviour change, stored progress:** a resumable keyset or incremental export now records the collection's UUID with its progress, so the next run after the collection was dropped and created again with other ids is refused `RIVET_STATE_CURSOR_STREAM_MISMATCH` (exit 5, both incarnations named) instead of reading 0 rows past the old anchor and ending exit 0; the remedy is `rivet state reset` (read the new collection from the start) or `rivet state accept` (keep the progress). Progress written before the upgrade records no UUID: the first run after the upgrade adopts it once and binds it from then on, so a collection replaced before that first run is not caught. Only an `Unauthorized` listing lifts the check; any other `listCollections` failure stops the run.
