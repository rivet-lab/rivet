- **A PostgreSQL `numeric` delivered as text dropped its display scale: `1.50` landed as `1.5`, `0.00` as `0`, `1000.000` as `1000`.** Behaviour change. A `numeric` read through the binary wire as text, that is a `numeric` under a `columns:` string override (bare or `NUMERIC(p,s)`), was rebuilt at the natural scale of its digits while the server's text carries the column's scale; exit 0, no warning. **Now** the text is the server's text for the same value: `1.50`, `0.00`, `1000.000`, `NaN` unchanged. A `numeric` read as a decimal, and a bare `numeric` with no override (already the server's text), keep their bytes; no other engine is affected. A PostgreSQL CDC export with `columns: { n: text }` on a `numeric` also changes in its snapshot leg (`1.5` becomes `1.50`, `10` becomes `10.00` for `NUMERIC(18,2)`): the snapshot leg read through the binary wire while the stream leg already delivered the server's text, so equal values were different strings in one `__changes` table and now match. Rows and tables written before the upgrade keep the shortened text, so a key column holding such a text (`10` before, `10.00` after) is two keys downstream, and the `row_hash` of those rows differs from the hash of the same rows written after. **What to do:** re-export the affected tables (a full export, or an incremental load deduplicated on the key; for CDC, a re-baseline of the table) when downstream code compares the text, parses its scale, joins on it or compares `row_hash`; nothing otherwise.
