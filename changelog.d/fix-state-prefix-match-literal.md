- **Behaviour change: on Postgres state, `cleanup_source` and `gc_orphans` no longer decide a live run is not there when its destination prefix holds a backslash.** The run-status ledger matched prefixes with `LIKE`, and Postgres reads a backslash in a `LIKE` pattern as an escape: a run live on `gs://b/vN/a\b/` was not found by its own per-table child `.../a\b/orders/`, so a CDC run's unmanifested part could be collected as crash debris (a partition run under `.../p\q/d=1/` was missed the same way). **Now** the ledger compares the prefix text itself (equal, or one under the other at a `/`), so backslash, `%`, `_` and letter case mean the same on SQLite and Postgres state. **Behaviour change on both backends:** a prefix that only looks like the live one (`a_b` against `aXb`, `a%b` against `aXYb`) is no longer treated as live, and on SQLite state a prefix that differs only in letter case (`Up/` against `up/`) is no longer treated as live, so gc and `cleanup_source` stop being held back by them; the one place that still differs is a local destination on a case-insensitive filesystem, where `Up/` and `up/` are one directory. Nothing stored changes shape, so the upgrade needs no step and the state written by the previous release is read as it is. **What to do:** nothing. A NUL byte in a prefix is not handled by this change (Postgres state cannot store one).
