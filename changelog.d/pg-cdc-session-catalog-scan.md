- **A PostgreSQL CDC session no longer reads the built-in array types of `pg_catalog` when it opens (behaviour change).** Each reader session read every array type of the server's type catalog, about 1800 source tuples, whatever tables the export captures, so a run that polls often paid that on every session. **Now** the open reads the domains, the array types of the database's own schemas and the array types of the built-in `information_schema` (about 80 rows), and each array type of `pg_catalog` is asked of the catalog once per session, the first time a change carries it. A database whose user-defined types are few opens on about 1600 tuples where it used to open on about 3100, and a session that meets a `pg_catalog` array type pays one catalog lookup for it. **The win exists only while the user-defined types are few:** the open grows with their number, and the check for a user-defined type that bears a `pg_catalog` name reads the user-defined types once. Measured on one server whose catalog had no gathered statistics, a catalog of 615 type rows opens on 1625 tuples against 3135 before, one of 1215 rows on 4325 against 5535, one of 5215 rows on 22325 against 21535 and one of 21215 rows on 94325 against 85535, so with thousands of user-defined types the open is not cheaper than before and is up to 10% dearer; on a catalog whose statistics were gathered the difference measured was within 1.5%. **What a stream delivers is the same as before** for every array column the open knew: each label is decided as the open decided it, so a type, schema or table renamed, a type moved to another schema or a type dropped after the open leave the delivered lists and server text as they were, and so do the arrays of `information_schema` domains such as `cardinal_number[]` and `sql_identifier[]` under a search path that names `information_schema`. When a user-defined type bears the name of a `pg_catalog` one (an `inet` type in `public` under a search path of `public, pg_catalog`), the open reads every array type as before. A label the catalog does not hold is asked once per session and stays a list, as before. No state, checkpoint or slot is touched, so nothing needs repair after the upgrade; **what to do:** nothing.
