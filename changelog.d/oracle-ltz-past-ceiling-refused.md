- **An Oracle `TIMESTAMP WITH LOCAL TIME ZONE` value stored outside Oracle's own 4712 BC to 9999 range is refused with `RIVET_SOURCE_VALUE_UNREPRESENTABLE` instead of being delivered a year off (behaviour change).** A session whose zone is ahead of UTC that writes a local-zone value within its offset of `9999-12-31 23:59:59` (or behind UTC, within its offset of 4712 BC) makes Oracle store a year past that end of its range, and it cannot print the value either (ORA-01877, ORA-01841); rivet read it through `SYS_EXTRACT_UTC` and delivered `10000-12-31 23:59:59` UTC as an exact instant, Parquet `253433923199000000` against `253402300799000000` for the same literal in a `TIMESTAMP WITH TIME ZONE` column, exit 0. **Now** a batch run that reads such a value, under the default mapping or under a `text`, `json`, `date` or `timestamp_ns` override, stops with exit 5 before any part is written and names the column; a CDC snapshot stops the same way, and the change stream stops with `RIVET_SOURCE_CDC_UNDECODABLE` (exit 5) because LogMiner cannot decode the change; a local-zone value inside the range is delivered as before, and so are `TIMESTAMP`, `DATE` and `TIMESTAMP WITH TIME ZONE` (a zoned value whose offset carries it past 9999 in UTC is still delivered exactly). **Remedy**, verified from the refused state: leave the column out of the export (list the other columns in a `query:`; a predicate on the column fails in Oracle itself), or rewrite the stored value from a UTC session (`ALTER SESSION SET TIME_ZONE = '+00:00'` then `UPDATE`). Files an older rivet already wrote keep their shifted instants; rivet does not rewrite them.
