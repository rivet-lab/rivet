- **An Oracle `TIMESTAMP WITH LOCAL TIME ZONE` value stored outside Oracle's own 4712 BC to 9999 range is refused with `RIVET_SOURCE_VALUE_UNREPRESENTABLE` instead of being delivered a year off (behaviour change).** A session whose zone is ahead of UTC that writes a local-zone value within its offset of `9999-12-31 23:59:59` (or behind UTC, within its offset of 4712 BC) makes Oracle store a year past that end of its range, and it cannot print the value either (ORA-01877, ORA-01841); rivet read it through `SYS_EXTRACT_UTC` and delivered `10000-12-31 23:59:59` UTC as an exact instant, Parquet `253433923199000000` against `253402300799000000` for the same literal in a `TIMESTAMP WITH TIME ZONE` column, exit 0. **Now** a batch run that reads such a value, under the default mapping or under a `text`, `json`, `date` or `timestamp_ns` override, stops with exit 5 before any part is written and names the column; a CDC snapshot stops the same way, and the change stream stops with `RIVET_SOURCE_CDC_UNDECODABLE` (exit 5) because LogMiner cannot decode the change; a local-zone value inside the range is delivered as before, and so is a real instant just past 9999 (`TIMESTAMP '9999-12-31 22:00:00 -05:00'` from any session, stored as 10000-01-01 03:00), exactly as a `TIMESTAMP WITH TIME ZONE` column holds it; at the 4712 BC floor every stored value before the range is refused, because the bytes Oracle keeps there do not tell a shifted value from an instant; and a `TIMESTAMP`, `DATE` or `TIMESTAMP WITH TIME ZONE` column holding a stored value is delivered as before (a zoned value whose offset carries it past 9999 in UTC is still delivered exactly). The refusal covers any timestamp or date value read past 9999 outside the 1 January 10000 window, whatever produced it: a `CAST` to `TIMESTAMP`, `TIMESTAMP WITH TIME ZONE` or `DATE`, a view that casts, `TRUNC`, `ADD_MONTHS`, `FROM_TZ`, `COALESCE`, `UNION ALL`, and the `text`, `json`, `timestamp_ns` and `date` overrides; this includes a value Oracle computes in a `query:` from a real year-10000 instant (for example `ADD_MONTHS(CAST(SYS_EXTRACT_UTC(z) AS DATE), 1)` over a `TIMESTAMP WITH TIME ZONE` value stored on 10000-01-01, which main delivered exactly and is now refused, because a computed value past the window cannot be told apart from a shifted one). **Limit:** `SELECT TRUNC(l, 'YYYY')` over a shifted row lands inside the delivered 1 January window and is delivered a year off with exit 0, on this version and on main alike; it cannot be told apart from `TRUNC` of a real instant. **Remedy**, verified from the refused state: leave the column out of the export (list the other columns in a `query:`; a predicate on the column fails in Oracle itself), or rewrite the stored value from a UTC session (`ALTER SESSION SET TIME_ZONE = '+00:00'` then `UPDATE`). Files an older rivet already wrote keep their shifted instants; rivet does not rewrite them.
