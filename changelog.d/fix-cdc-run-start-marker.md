- **Behaviour change: a CDC run writes a `running` manifest for each table before its first part, so a `rivet load` with `gc_orphans` from another state DB no longer deletes the part of a run still writing** (all CDC engines; seen on the ClickHouse load cells over MySQL and PostgreSQL). Until now the first part of a CDC run was uploaded before any manifest named the run; a load started from a fresh state DB beside the config, with `gc_orphans: true`, saw only the bucket, took that part for an orphan and removed it, and the next load refused the run's manifest as declaring parts that are no longer under the prefix (0.32.2 and earlier). **Now** the run first writes `manifest-<run>.json` with `status: running` and no parts under its own run-unique name; the first roll rewrites it as `success`, and a run that fails before its first manifest removes it when no part of the table reached the store, or overwrites it as `failed` over the parts that did. The canonical `manifest.json` and `_SUCCESS` are untouched. The marker is a new object under the CDC prefix of each table, written once per run per table. **What to do:** nothing for a run that ends. A run killed before its first manifest leaves its `running` marker, and a load keeps every part of that run until a newer CDC run of the same export succeeds, so run the export once more (`rivet run`) to its normal end: that run's manifest supersedes the stale marker. Upgrade: no state or destination step; a prefix written by 0.32.1 keeps its manifests unchanged and the first run of this version appends beside them (checked: 0.32.1 runs, then this version's run onto the same prefix, exit 0 each time, every row delivered once).
