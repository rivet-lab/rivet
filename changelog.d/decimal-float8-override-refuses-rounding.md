- **A `columns:` override that declares a source decimal `float8` is no longer labelled `exact`, and a value the double would round now stops the run with `RIVET_SOURCE_VALUE_UNREPRESENTABLE` (behaviour change).** MySQL `DECIMAL`, SQL Server `money`, and Oracle `NUMBER`, declared `float8`, were delivered rounded to the nearest double with exit 0 (`922337203685477.5807` arrived as `922337203685477.6`, `9007199254740993` as `9007199254740992`), and `rivet check` reported the pair as fidelity `exact`. **Now** `check` reports a `float8` override over a decimal of precision above 15 as `lossy`, and a batch or CDC run delivers a decimal only when the double prints back the same digits (always for up to 15 significant digits, and for the integers up to 2^53), otherwise it stops before any part is written with exit 5 naming the column and the value; PostgreSQL still refuses the pair, and a MySQL text column declared `float8` follows the same rule. An export whose values fit (cents, ids below 2^53) is unchanged and its output bytes are the same as before. Remedy for an export that now stops: declare `decimal(p,s)` for the column in `columns:` (the digits are kept) or remove the override; no state or table written before the upgrade needs a repair, and a table that already holds rounded doubles is only cured by a re-export of the column as `decimal(p,s)`.
