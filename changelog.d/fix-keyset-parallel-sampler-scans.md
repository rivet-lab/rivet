- **Parallel keyset (`chunk_by_key` + `parallel: N`) counted every row of the source and then skipped through the key index to each percentile before the first worker started, so setup cost grew with the table: on a 4M-row PostgreSQL table it read 4M rows sequentially and 10M index entries on top of the export itself (since 0.23.0, #1059).** **Now** the range sampler reads the key's MIN and MAX, splits that span evenly by value (integer, float, uuid, date, timestamp or text) and snaps each cut to the next existing key: N+1 index seeks at any table size, no count and no offset skip. Every row is still read exactly once and every row of one lead value stays in one range; resume and checkpoints are unchanged. Behaviour change: the ranges are balanced by key value, not by row count, so a skewed key (most rows in one corner of its span, or a few far outliers) gets uneven ranges, down to a single worker with the existing warning. **What to do:** nothing for an evenly spread key (a sequence, a random or time-ordered uuid); for a skewed key, run it with `parallel: 1` or a range `chunk_column`.
