- **Parallel keyset (`chunk_by_key` + `parallel: N`) counted every row of the source and then skipped through the key index to each percentile before the first worker started, so setup cost grew with the table: on a 4M-row PostgreSQL table it read 4M rows sequentially and 10M index entries on top of the export itself (since 0.23.0, #1059).** **Now** rivet reads the table's row estimate from the catalog (PostgreSQL `reltuples`, MySQL `TABLE_ROWS`, SQL Server `sys.partitions`, Oracle `NUM_ROWS`; never a count). Under 10M rows the ranges are the same exact row percentiles as before. At 10M rows or more, or with no estimate, the sampler reads the key's MIN and MAX, splits that span evenly by value (integer, float, uuid, date, timestamp or text) and snaps each cut to the next existing key by an index seek: no count and no offset skip at any table size. An integer key is cut into 16 ranges per worker (at most 256), at most N running at once. Every row is still read exactly once and every row of one lead value stays in one range; resume and checkpoints are unchanged.
- **Incremental parallel keyset on a PostgreSQL `uuid` key failed with `function max(uuid) does not exist`.** The run's upper bound is now read by an index seek (`ORDER BY key DESC`), which works for every key type the cursor reads.
- **`apply --pool --split` on a keyset key the catalog puts at 10M rows or more now cuts its units by key value**, from the same seeks, instead of counting the table.
- **Behaviour change, above 10M catalog rows or with no estimate (a `query:` export, an unanalyzed table):** the ranges are balanced by key value, not by row count, so a skewed key gets uneven ranges, down to a single worker with the existing warning; an integer key now writes up to 16N range part files (`pk_w0` … `pk_w255`) instead of N, with at most N source connections at a time. If the server cannot read a split point back, the keys above the last good cut stay in one range with a warning instead of failing the run. **What to do:** nothing for an evenly spread key (a sequence, a random or time-ordered uuid) or a table under 10M rows; for a skewed key above 10M rows, run it with `parallel: 1` or a range `chunk_column`. Exports written before the upgrade need nothing: the range layout is planned per run and stored with the run's ranges.
