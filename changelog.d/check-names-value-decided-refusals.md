- **`rivet check` says which refusals a value it did not read can still raise.** Before, `rivet check` exited 0 on an export whose run then refused a value with `RIVET_SOURCE_VALUE_UNREPRESENTABLE` or `RIVET_LOAD_VALUE_OUT_OF_TARGET_RANGE`, with no hint that check reads at most the first row of an export that declares `columns:`. **Now**, for an export whose `columns:` map is not empty, check prints `note[values-unread]: rivet check reads at most the first row of an export that declares `columns:`; a run may still refuse a value it did not read with RIVET_SOURCE_VALUE_UNREPRESENTABLE, RIVET_LOAD_VALUE_OUT_OF_TARGET_RANGE` on stderr; its exit code and stdout are unchanged. `docs/reference/errors.md` lists these codes under "Decided by a value". **What to do:** nothing; a script that parses check's stderr should skip lines starting with `note[`.
- **Behaviour change, exit 1 to exit 5: a value an override cannot hold is refused with the value code on SQL Server, Oracle, and on a CDC snapshot and stream, as MySQL and PostgreSQL do; MySQL text under an integer override is refused instead of cut to its leading digits.** Before, a `columns:` override refused by a value it could not hold (an Oracle `DATE` or `TIMESTAMP` with a time of day under `date`, an Oracle `RAW` of the wrong length under `uuid`, SQL Server text that is not a uuid under `uuid`, a SQL Server decimal whose digits a narrower scale would drop; and on a CDC snapshot or stream, an integer past the declared width or text that is not an integer) stopped with `RIVET_SOURCE_OVERRIDE_WIRE_MISMATCH` (exit 1, a usage error), while the same case on MySQL and PostgreSQL batch stopped with `RIVET_SOURCE_VALUE_UNREPRESENTABLE` (exit 5, a refusal); an Oracle CDC export gave exit 5 on its snapshot leg and exit 1 on its stream leg for the same value. MySQL batch read a text cell such as `1.5` under an `int32` override as `1`. **Now** every engine and every leg uses `RIVET_SOURCE_VALUE_UNREPRESENTABLE` (exit 5) for a value-decided refusal, and a MySQL text cell is an integer only when the whole cell is one (`1.5`, `1e3`, `12abc`, empty, `-` are refused). `RIVET_SOURCE_OVERRIDE_WIRE_MISMATCH` (exit 1) stays for a pair the reader cannot build (numeric, float or text under an integer override on PostgreSQL, SQL Server and Oracle; DECIMAL and DOUBLE on MySQL). Only the code and exit change; what a run writes before it stops does not: a chunked export refused at a later chunk keeps the parts of the chunks it finished and a manifest whose run is `failed`, as before, and `rivet check` still exits 0 when the refusing value is not in the first row. No state or table written before the upgrade changes. **What to do:** a script that matched `RIVET_SOURCE_OVERRIDE_WIRE_MISMATCH` or exit 1 for these cases must match `RIVET_SOURCE_VALUE_UNREPRESENTABLE` and exit 5; a scheduler that retries on exit 1 and stops on 5 now stops, which is right, since the value will not change on retry; a MySQL export that relied on text being cut to its leading digits must declare the column `decimal` or `float64`, or clean the text.
