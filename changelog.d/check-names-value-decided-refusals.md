- **`rivet check` says which refusals a value it did not read can still raise.** Before, `rivet check` exited 0 on an export whose run then refused a value with `RIVET_SOURCE_VALUE_UNREPRESENTABLE` or `RIVET_LOAD_VALUE_OUT_OF_TARGET_RANGE`, with no hint that check reads at most the first row of an export that declares `columns:`. **Now**, for an export whose `columns:` map is not empty, check prints `note[values-unread]: rivet check reads at most the first row of an export that declares `columns:`; a run may still refuse a value it did not read with RIVET_SOURCE_VALUE_UNREPRESENTABLE, RIVET_LOAD_VALUE_OUT_OF_TARGET_RANGE` on stderr; its exit code and stdout are unchanged. `docs/reference/errors.md` lists these codes under "Decided by a value". **What to do:** nothing; a script that parses check's stderr should skip lines starting with `note[`.
- **Behaviour change, exit 1 to exit 5: a value an override cannot hold is refused with the value code on SQL Server, Oracle, and on a CDC snapshot and stream, as MySQL and PostgreSQL do; MySQL text under an integer override is refused instead of cut to its leading digits.** Before, a `columns:` override refused by a value it could not hold (an Oracle `DATE` or `TIMESTAMP` with a time of day under `date`, an Oracle `RAW` of the wrong length under `uuid`, SQL Server text that is not a uuid under `uuid`, a SQL Server decimal whose digits a narrower scale would drop; and on a CDC snapshot or stream, an integer past the declared width, text that is not an integer, or a decimal with more fraction digits than the declared scale, on the SQL Server stream) stopped with `RIVET_SOURCE_OVERRIDE_WIRE_MISMATCH` (exit 1, a usage error), while the same case on MySQL and PostgreSQL batch stopped with `RIVET_SOURCE_VALUE_UNREPRESENTABLE` (exit 5, a refusal); an Oracle CDC export gave exit 5 on its snapshot leg and exit 1 on its stream leg for the same value. MySQL batch read a text cell such as `1.5` under an `int32` override as `1`. **Now** every engine and every leg uses `RIVET_SOURCE_VALUE_UNREPRESENTABLE` (exit 5) for a value-decided refusal, and a text cell is an integer only when the whole cell is one, on MySQL batch and on every CDC leg through the same function (`1.5`, `1.0`, `1e3`, `12abc`, empty, `-`, and a cell with a leading or trailing space are refused; a MySQL CDC stream used to deliver `1.0` and ` 1` as `1`). `RIVET_SOURCE_OVERRIDE_WIRE_MISMATCH` (exit 1) stays for a pair the reader cannot build (numeric, float or text under an integer override on PostgreSQL, SQL Server and Oracle; DECIMAL and DOUBLE on MySQL). Only the code and exit change; what a run writes before it stops does not: a chunked export refused at a later chunk keeps the parts of the chunks it finished and a manifest whose run is `failed`, as before, and `rivet check` still exits 0 when the refusing value is not in the first row. No state or table written before the upgrade changes. **What to do:** a script that matched `RIVET_SOURCE_OVERRIDE_WIRE_MISMATCH` or exit 1 for these cases must match `RIVET_SOURCE_VALUE_UNREPRESENTABLE` and exit 5; a scheduler that retries on exit 1 and stops on 5 now stops, which is right, since the value will not change on retry; a MySQL export that relied on text being cut to its leading digits, or on a CDC stream reading `1.0` as `1`, must declare the column `decimal` or `float64`, or clean the text.
- **Behaviour change, stream-only CDC export: a numeric, float or text column under an integer `columns:` override is refused at plan time on every engine where the batch run refuses it.** Before, a `mode: cdc` export that had no baseline leg (`initial` not `snapshot`) never read the override table: a PostgreSQL `numeric(10,2)` declared `int8` delivered `43.00` as `43`, and a PostgreSQL, SQL Server or Oracle text column declared `int64` delivered `'2'` as `2`, while the baseline leg of the same config, `rivet check` and a batch run stopped. **Now** the run, `rivet check` and `rivet check --type-report` read the same table on the stream and on the baseline leg, and the stream stops before any change is read with `RIVET_SOURCE_OVERRIDE_WIRE_MISMATCH` (exit 1) naming the column, its native type and the declared type; a stream refused for a value (`RIVET_SOURCE_VALUE_UNREPRESENTABLE`, exit 5) is only a value the table reads but the type cannot hold. MySQL text under an integer override is read by the table and stays value-decided. A CDC checkpoint, part or table written before the upgrade is unchanged. **What to do:** remove the override and let the column keep its decimal, float or text type, or declare the type the column is (for a numeric with a scale `decimal(p,s)`), then run `rivet check`; a `mode: cdc` export has no `query:` to CAST in.
