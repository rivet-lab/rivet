- **A `columns:` override that drops sub-microsecond digits is reported lossy, not exact.** Before, declaring `timestamp` or `timestamp_tz` over an Oracle `TIMESTAMP(7..9)` or a SQL Server `datetime2(7)` / `datetimeoffset(7)` truncated the digits below a microsecond while the type report and the manifest said fidelity `exact`, and `rivet validate --depth full` passed. **Now** such a column is fidelity `lossy` with a warning that names the nanosecond declaration; under the default policy the run still exits 0, and `--strict` refuses it as it does any lossy column. **What to do:** to keep the digits, declare `timestamp_ns` / `timestamp_tz_ns` or drop the override; to accept the truncation, nothing. On SQL Server the scale comes from the catalog, which rivet reads only for a `table:` export or a `query:` that is a plain single-table `SELECT`; a `query:` with a join or a subquery over a `datetime2(7)` column under `timestamp` is still reported `exact` while the digits are truncated, so declare `timestamp_ns` there.
