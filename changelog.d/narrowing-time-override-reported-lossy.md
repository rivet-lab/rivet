- **A `columns:` time override that keeps fewer fraction digits than the column the query returns is reported lossy, not exact, on batch and on CDC (behaviour change under `--strict`).** Before, declaring `timestamp`, `timestamp_tz` or `date` over an Oracle `TIMESTAMP(7..9)`, a SQL Server `datetime2(7)` or `datetimeoffset(7)` truncated the digits below a microsecond while `rivet check`, the type report and the run said fidelity `exact`, and `rivet validate --depth full` passed. **Now** such a column is fidelity `lossy` with a warning that names the cause and the remedy. The verdict follows the column the query returns, read from the source for the query as written: an alias (`d7 AS x`, `x: timestamp`) and a join are `lossy`, a `CAST` to a coarser type (`CAST(d7 AS datetime2(3)) AS d7`) or a column that is not finer than a microsecond stays `exact`. When SQL Server cannot describe the query, or the source cannot answer, the column is graded `lossy` with the cause in the warning, never `exact` in silence. The CDC run reads its columns the same way, so a `--strict` CDC run sees what `check` reports; the same grading now reaches a CDC export that declares a decimal narrower than its source. Under the default policy the run still exits 0 and the column reads `lossy` in `rivet check --type-report`; **`--strict` now refuses** such a config with `RIVET_TYPE_UNSAFE_MAPPING` before any row is read, where it ran before. **What to do:** to keep the digits, drop the override on SQL Server (`datetime2(7)` and `datetimeoffset(7)` keep nanoseconds by default) or declare `timestamp_ns` on an Oracle `TIMESTAMP(7..9)` and `timestamp_tz_ns` on an Oracle `TIMESTAMP(7..9) WITH TIME ZONE`; to accept the truncation, run without `--strict`. Data already delivered is unchanged: only the label and the `--strict` verdict move, nothing is re-exported.
