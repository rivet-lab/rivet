- **A MySQL DATE, DATETIME or TIMESTAMP column whose zero or partial dates were written as NULL claimed `rivet.fidelity: exact`, and `validate` and `--reconcile` passed without saying so (#994).** Behaviour change. The #951 decision stands: the value is NULL and the run warns with the per-column count. **Now** the field metadata of every MySQL `date`, `datetime` and `timestamp` column (batch and CDC) is `rivet.fidelity: compatible`, because a zero date can sit in any such column and the label is written before the first row is read; the run records the per-column count in its manifest as the additive field `nulled_cells`, `rivet validate` prints it as the warning `RIVET_VERIFY_CELLS_WRITTEN_AS_NULL` (the verdict and the exit code are unchanged) and the `reconcile` row of a run summary names it after the counts. Parquet written before the upgrade keeps `exact` in its metadata and manifests written before it carry no count; nothing is rewritten. **What to do:** a consumer that read `rivet.fidelity: exact` as "no value was changed" should read `compatible` on these columns as "a zero or partial date may be NULL" and take the count from the run warning or `rivet validate`; `--strict` does not refuse `compatible`.
