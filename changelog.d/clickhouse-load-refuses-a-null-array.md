- **`rivet load` into ClickHouse refuses a part holding a NULL array, before creating a table or inserting anything.** Behaviour change. Before, a NULL in a PostgreSQL array column (`TEXT[]`, `INTEGER[]`, `DOUBLE PRECISION[]`, `DATE[]`, `TIMESTAMP[]`, `TIMESTAMPTZ[]`, `TIME[]`, `BYTEA[]` and the rest) was loaded as `[]`, because a ClickHouse `Array` cannot be NULL: NULL and an empty array became the same value, silently. **Now** a part whose list column holds a NULL list is refused with `RIVET_LOAD_VALUE_OUT_OF_TARGET_RANGE` (exit 5, a refusal) naming the column; nothing is created or inserted, for a full load, an incremental load and a change log alike. An empty array, an array holding NULL elements and a column without NULL arrays load as before, and so does a change-log delete, whose non-key columns are NULL by construction. `rivet check --type-report --target clickhouse` names the refusal in the list column's note. A table loaded before the upgrade is not touched: the `[]` it already holds stays, and no new load of the same data succeeds. **What to do:** for a batch export, in the export's `query:` read the column as `COALESCE(a, '{}') AS a` to load `[]` on purpose, or as `a::text AS a` to keep the NULL in a `String` column, or correct the value at the source. A `mode: cdc` export has no `query:`, and the part that holds the NULL stays staged, so fixing the source alone does not lift the refusal on the next load: give every row a list in the source, then re-baseline the stream (the refusal prints the recipe: delete the checkpoint, move the destination's files out, delete the export's `cdc_snapshot` rows, set `cdc.initial: snapshot`, truncate `<table>__changes`, run); a `columns:` override does not help, since PostgreSQL does not convert a list to text. To find the rows an earlier load emptied, compare the table's `[]` rows with the source rows where the array is NULL.
