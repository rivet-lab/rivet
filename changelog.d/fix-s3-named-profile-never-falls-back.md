- **An S3 `aws_profile` was replaced by an ambient identity.** The profile was resolved with the environment layered over it: an `AWS_PROFILE` naming another profile selected that profile's keys, `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` replaced the named profile's keys, and a profile that did not exist or held no static keys (an SSO or login profile) fell through to environment keys or the EC2 instance-metadata service, so a run wrote under an identity the operator did not name, or hung off-EC2. **Behaviour change.** **Now** only the named profile is read from the shared AWS files, and the store stops with `RIVET_DEST_CREDENTIALS_INVALID` (before any request) when the profile is missing or holds neither static keys nor a `role_arn` + `web_identity_token_file`, or when the environment sets `AWS_PROFILE` to another profile; ambient access keys no longer override the profile's, and instance metadata is never asked. **Changed stops:** an `aws_profile` that only worked through ambient env keys or IMDS, and a run started with `AWS_PROFILE` set to another name, are now refused. **What to do:** add static keys to the profile, or export temporary keys with `aws configure export-credentials --format env` and use `access_key_env` / `secret_key_env` / `session_token_env`, or remove `aws_profile` to use the ambient AWS chain; run with `env -u AWS_PROFILE rivet ...` or set `aws_profile` to the `AWS_PROFILE` value.
