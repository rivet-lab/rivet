- **An undeclared Oracle `TIMESTAMP(7..9)` column, plain, `WITH TIME ZONE` or `WITH LOCAL TIME ZONE`, is delivered as nanosecond text on batch and on CDC instead of being refused.** Behaviour change. Before, a run, `rivet check` and a CDC stream over such a column stopped with `RIVET_TYPE_UNSAFE_MAPPING` until a `columns:` entry declared it. **Now** the column is a `Utf8` string `YYYY-MM-DDTHH:MM:SS.fffffffff` with all nine fraction digits in any year (an astronomical year past 9999 or before year 1 keeps its sign), a trailing `Z` and UTC for the two zoned types, and the type report names it `text:iso_timestamp_nanos`. The batch snapshot, the CDC snapshot and the CDC stream print the same text for the same value. A declared `timestamp_ns` or `timestamp_tz_ns` still delivers a native nanosecond timestamp (years 1677 to 2262 only), a declared `timestamp` or `timestamp_tz` still reads microseconds and is `lossy` (refused under `--strict`), and `columns: {COL: string}` is unchanged. A `TIMESTAMP(7..9)` incremental cursor and a keyset key are still refused, and an Oracle `WITH LOCAL TIME ZONE` value outside 4712 BC to 9999 is still `RIVET_SOURCE_VALUE_UNREPRESENTABLE`. A keyed load over such a column as its `pk:` is no longer refused as landing at microseconds, because the text keeps every digit. Tables and state written before the upgrade are untouched: the run used to stop before writing, so no file of this column exists, and an export that already declares the column keeps its declared type. **What to do:** nothing to keep the column; to land it as a timestamp, declare `timestamp_ns` (or `timestamp_tz_ns`) under `columns:` for the export, or cast it in the export's `query:`.
