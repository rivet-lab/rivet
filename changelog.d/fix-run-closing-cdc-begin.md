- **A CDC run over a state that would not take its run-status row read its stream and wrote anyway, and a load that did not see the run's row recorded the run consumed while it was still writing.** A `mode: cdc` run opened its run-status row warn-only, so over a state that refused the write (a read-only or full state DB) it ran with no row, and a `rivet load` whose own state DB held no row for the run counted it finished: it loaded the parts of one roll and recorded the run consumed, so the parts the run wrote in later rolls were never loaded and the next load printed "up to date" with exit 0 (a ClickHouse table held ids 1..8 of 1..14). **Now** a CDC run opens its row through the same call a batch run does and stops before it reads its stream when the state refuses it, and a load treats a CDC run it holds no ledger row for as still writing until a newer CDC run of the same family exists. **Changed stops:** a CDC run over a state that refuses the run-status row ends `RIVET_STATE_NOT_WRITABLE` (exit 1) with nothing written, not exit 0. **Behaviour change in `rivet load`:** the newest CDC run with no ledger row in the load's state is loaded again on every cycle and not recorded consumed (at-least-once, which the current-state view absorbs), the load prints the "source run(s) still writing" note for it, and `cleanup_source` keeps its parts; a newer CDC run of the same family ends the state. A load without a state DB, a batch run with no row, a run with a row (finished or running) and a `running` marker are read as before. **What to do:** after `RIVET_STATE_NOT_WRITABLE`, make the state DB writable and run again; to stop a load re-reading the newest run, point the load at the state DB the extract writes (or run the export once more). Nothing in the state or in earlier tables changes shape; runs a load recorded consumed before the upgrade stay recorded.
