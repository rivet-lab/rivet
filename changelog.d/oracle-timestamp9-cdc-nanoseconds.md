- **An Oracle change-data-capture run now delivers every fractional digit of a `TIMESTAMP(7..9)` column declared `timestamp_ns` / `timestamp_tz_ns` or `text`, as batch does, and refuses a value past the nanosecond range with `RIVET_SOURCE_VALUE_UNREPRESENTABLE` (exit 5).** Behaviour change. The stream leg read the LogMiner text at microseconds, so `.123456789` arrived as `.123456` in a nanosecond or text column while the snapshot leg and batch delivered the nine digits, with exit 0; a value outside 1677-09-21..2262-04-11 under a nanosecond column stopped the stream as `RIVET_SOURCE_OVERRIDE_WIRE_MISMATCH` (exit 1) where batch exits 5. **Now** the stream keeps the nine digits and the refusal is the batch one, naming the column and the remedy. A column declared `timestamp` still delivers microseconds on batch and on the stream, and an undeclared `TIMESTAMP(7..9)` is still refused by both (`RIVET_TYPE_UNSAFE_MAPPING`). Tables written before the upgrade keep their truncated stream rows: rows the stream delivered earlier are not rewritten. **What to do:** to repair them, re-run the snapshot (`initial: snapshot` with a fresh `__changes` table) or re-export the table in batch; rows delivered after the upgrade are exact. A run that stopped on the out-of-range value with exit 1 now stops with exit 5, so a wrapper keyed on exit 1 for that stop should read the code.
- **A change-data-capture run now writes a timestamp or date column declared `text` in the same text the batch export and the snapshot write, on Oracle and MySQL.** Behaviour change. The stream printed the instant in one form for every engine (a space between date and time, the fraction cut at its last non-zero digit or absent), so one column held two texts for one instant: Oracle `2024-02-29T13:14:15.500000` on batch and snapshot against `2024-02-29 13:14:15.500` on the stream, and MySQL `2024-02-29 13:14:15.500000` against `2024-02-29 13:14:15.500` (and `...15` for a whole second). **Now** the stream writes Oracle's `SYYYY-MM-DDTHH24:MI:SS.FF6` (nine digits when finer) and MySQL's `YYYY-MM-DD HH:MI:SS.ffffff`, from the same functions batch calls. A column with a typed override or none is unchanged, and so is every other engine: SQL Server refuses `text` over a timestamp on every leg, and a PostgreSQL stream keeps its text. **Three disagreements of batch and stream under `text` remain, each an open defect recorded in `dev/release_oracle/known_red.py` and not fixed here:** a PostgreSQL `timestamp` is refused by batch with `RIVET_SOURCE_OVERRIDE_WIRE_MISMATCH` (exit 1) while the stream writes chrono's text; a MySQL zero datetime (`0000-00-00 00:00:00`) is `0000-00-00 00:00:00.000000` on batch and NULL on the stream; an Oracle DATE only the Julian calendar holds (`1500-02-29`) is delivered by batch and refused by the stream with `RIVET_SOURCE_CDC_CELL_UNSUPPORTED`. Every other value is the batch text. Rows the stream wrote before the upgrade keep the old text and are not rewritten. **What to do:** a consumer that parsed the old stream text should read the batch form; to repair rows already written, re-run the snapshot (`initial: snapshot` with a fresh `__changes` table) or re-export the table in batch.
