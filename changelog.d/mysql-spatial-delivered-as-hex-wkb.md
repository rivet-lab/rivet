- **A MySQL spatial column (`GEOMETRY`, `POINT`, `LINESTRING`, `POLYGON`, `MULTIPOINT`, `MULTILINESTRING`, `MULTIPOLYGON`, `GEOMETRYCOLLECTION`) is delivered as the lowercase hex of its standard WKB, in batch and CDC, instead of being refused with `RIVET_TYPE_UNSAFE_MAPPING`.** Behaviour change. Before, a batch export, `rivet check` and a CDC snapshot of such a column stopped before any write. **Now** the column is a `Utf8` column labelled `rivet.text_form: hex_wkb`, equal to `LOWER(HEX(ST_AsBinary(col)))`; a warehouse recovers the geometry with BigQuery `ST_GEOGFROMWKB`, Snowflake `TO_GEOMETRY` or ClickHouse `readWKB*(unhex(x))` (25.8 or later). WKB holds no SRID, and a geographic SRS stores its axes in the other order than `ST_AsBinary` writes them, so a value whose SRID is not 0 is refused `RIVET_SOURCE_VALUE_UNREPRESENTABLE` (exit 5) naming the column and its SRID; it is never delivered without its SRS. A full or incremental export writes no part before that stop; a `mode: chunked` export has already written the parts of the chunks it read before the refused one (a probe wrote 4 parts), so re-run it after the remedy. In a batch export and in the CDC snapshot, `tuning.max_value_mb` is read on the bytes MySQL holds, as for a `binary` column, not on the doubled hex; a binlog event carries no value ceiling for any column, which this change does not alter. A column declared `string` or `binary` in `columns:` is unchanged, except that the Parquet field metadata `rivet.native_type` of a `binary` override reads `geometry` where it read `unknown` (the values are unchanged). **Upgrade:** tables written before the upgrade are untouched, since a run that refused a spatial column wrote none. That run did record the column as `unknown` in the schema baseline; the first run after the upgrade rewrites it to the delivered `Utf8` without reporting drift, under `on_schema_drift: fail` (no exit 4) and under the default `warn` (no warning), proven by running the previous release and then this build on the same state. A CDC baseline written by 0.32.2 or 0.33.0 already holds the spatial column as `Utf8` and reads no drift either; a spatial column added to a CDC stream after the upgrade is a new column and drifts like any other (exit 4 under `fail`, `added: g` under `warn`). **What to do:** for an SRID other than 0 declare the column `binary` in `columns:` to carry MySQL's internal bytes (4-byte little-endian SRID, then WKB), or in a batch export select `ST_AsBinary(col)` and `ST_SRID(col)` in the `query:`; in a CDC stream declare it `binary` or leave the column out of the capture.
