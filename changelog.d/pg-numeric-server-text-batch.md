- **A PostgreSQL `numeric` with no declared precision and an array of `numeric` are now delivered by a batch export as the server's text, not refused with `RIVET_TYPE_UNSAFE_MAPPING` (behaviour change).** Through the previous release a batch export (every mode) of a bare `numeric` (an ad-hoc expression, or a column whose precision the catalog hint cannot carry such as `numeric(1000,0)`), of `numeric[]` or of `numeric(10,2)[]` stopped before any file was written, asking for a `columns:` declaration, while the change stream of the same column already carried the server's text, so one column was refused by one path and delivered by the other. **Now** both paths deliver a `string` column (`Utf8`, `rivet.text_form = server_text`) holding what the server prints (`1.50`, `NaN`, `-Infinity`, `{1.5,NULL}`), NULL where the source is NULL. A `numeric(p,s)` column of a table, which the catalog types, is unchanged and keeps its decimal. Tables and state written before the upgrade are untouched: an export that was refused wrote nothing. **What to do:** nothing; a downstream table that expected the column typed reads it as a string, and a typed column comes from a table column declared `numeric(p,s)`. A PostgreSQL `tsvector` declared `text` is unchanged and delivers the server's text (`'a' 'b' 'c'`).
