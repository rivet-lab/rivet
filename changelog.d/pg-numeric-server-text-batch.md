- **A PostgreSQL `numeric` with no declared precision and an array of `numeric` are now delivered by a batch export as the server's text, not refused with `RIVET_TYPE_UNSAFE_MAPPING` (behaviour change).** Through the previous release a batch export (every mode) of a bare `numeric` (an ad-hoc expression, or a column whose precision the catalog hint cannot carry such as `numeric(1000,0)`), of `numeric[]` or of `numeric(10,2)[]` stopped before any file was written, asking for a `columns:` declaration, while the change stream of the same column already carried the server's text, so one column was refused by one path and delivered by the other. **Now** both paths deliver a `string` column (`Utf8`, `rivet.text_form = server_text`) holding what the server prints (`1.50`, `NaN`, `-Infinity`, `{1.5,NULL}`), NULL where the source is NULL. A `numeric(p,s)` column of a table, which the catalog types, is unchanged and keeps its decimal. A refused first run of the previous release wrote no data file but did store the column's native name (`numeric`, `_numeric`) as the table's schema-drift baseline in `.rivet_state.db`; the first run after the upgrade reads that name as the same column now delivered as server text and rewrites the baseline to `Utf8` without reporting drift, in every batch mode (full, incremental, chunked by range or keyset) and in the CDC initial snapshot, under `on_schema_drift: fail` and the default policy alike, delivering each row once. A baseline that names a different column type is still drift. `rivet check --strict` no longer exits 1 for a bare `numeric` (it is not a refusal any more, the report says `logical_string`); it still exits 1 for a type that is refused, such as a `numeric(10,2)` read through a `float8` override. **What to do:** nothing; a downstream table that expected the column typed reads it as a string, and a typed column comes from a table column declared `numeric(p,s)`. A PostgreSQL `tsvector` declared `text` is unchanged and delivers the server's text (`'a' 'b' 'c'`).
