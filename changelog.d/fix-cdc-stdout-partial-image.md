- **Behaviour change: `rivet cdc` (with or without `--output`) and `rivet run` with `mode: cdc` refuse a change with a partial row image instead of delivering it.** On MySQL a change written under `binlog_row_image` = `MINIMAL` or `NOBLOB` (a session override counts) was printed to stdout as positional values with no column names (`"after":["C1x"]` for a four-column table), the run exited 0 and the checkpoint moved past it (0.32.2 and earlier); an SQL Server capture instance with fewer columns than its table did the same (`after=[1, 10, 1000]` for a four-column table), and without `--table` it did so with no check at all. A before image short of its column names under a whole after image (`NOBLOB` with only a `TEXT` column changed; `MINIMAL` with every column set) was delivered too: printed positionally on stdout, and written by `rivet cdc --output` and `mode: cdc` as the whole after image with exit 0, where a primary-key move under `MINIMAL` was written as a plain update because the old key could not be read from the short before image (the old key's row stayed live downstream). A partial after image was already refused by `--output` and `mode: cdc`. **Now** every sink stops with `RIVET_SOURCE_CDC_PREREQUISITE` (exit 1, or exit 2 when its cause is transient) before the line or the row, naming the table and the counts, and the checkpoint does not move past it, so a repeat is refused the same way. **Changed stops:** (1) a stdout drain that meets a partial after or before image of a listed table; (2) a stdout drain opened while the MySQL global `binlog_row_image` is `MINIMAL` or `NOBLOB`, even when only unlisted tables were written; (3) a stdout drain of an SQL Server capture instance that omits a column of its table, now with or without `--table`; (4) `rivet cdc --output` and `rivet run` with `mode: cdc` that meet an update whose before image is short of its columns under a whole after image. Whole images, PostgreSQL key-only deletes, unlisted tables and `--max-events 0` are delivered as before. **What to do:** set `binlog_row_image = FULL` for every writer (and enable the SQL Server capture instance with the full column list), then follow the printed steps: for `rivet cdc` alone on MySQL, delete the checkpoint file and drain once to re-anchor; `rivet run` with `mode: cdc` follows the `Re-baseline the stream in one run:` steps the refusal prints (the checkpoint file if there is one, the export's destination files, its `cdc_snapshot` rows, `cdc.initial: snapshot`, and a consuming warehouse load's `<table>__changes` table), because deleting the checkpoint file alone is refused with `RIVET_SOURCE_CDC_CHECKPOINT_INVALID` (exit 5); the open-time refusals print the setting to change instead; changes written before that anchor are not delivered again, so re-sync the consumer from the table. A checkpoint written before the upgrade stays valid and the previous binary resumes the new one's: a pre-upgrade run that already delivered a partial line or row is not repaired (nothing marks it afterwards), a pending partial change is refused on the first run after the upgrade; verified with a run of the previous binary followed by this one on the same checkpoint, then the re-baseline, a FULL update delivered whole and the previous binary resuming the checkpoint.
