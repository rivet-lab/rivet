- **Behaviour change**: a SQL Server `datetime2(7)` or `datetimeoffset(7)` column (scale above 6) is delivered as a nanosecond timestamp (`Timestamp(ns)`, ClickHouse `DateTime64(9, 'UTC')`) on batch and on CDC, so the 7th digit (the 100 ns tick) is kept instead of dropped to microseconds. `datetime2(0..6)`, `datetime` and `smalldatetime` are unchanged. A nanosecond timestamp holds 1677-09-21..2262-04-11: a value outside it stops the run with `RIVET_SOURCE_VALUE_UNREPRESENTABLE` (before the upgrade it landed at microseconds over 0001..9999). A scale-7 column that the keyset or chunk key refusal (`RIVET_PLAN_CHUNK_KEY_UNUSABLE`) used to stop is now admitted, and `rivet init` scaffolds it. Remedy for the old landing: declare the column `timestamp` (or `timestamp_tz`) under the export's `columns:`. Warehouse tables written before the upgrade are not rewritten, and BigQuery lands every nanosecond timestamp column, naive or zoned, as INT64 nanoseconds since the epoch (verified live), so a BigQuery table written before the upgrade as TIMESTAMP changes type: declare the column `timestamp` or `timestamp_tz` to keep it.
