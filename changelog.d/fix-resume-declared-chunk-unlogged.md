- **A resumed range-chunk run finalized a manifest declaring a chunk whose `file_log` row was never written.** A run that failed after a chunk's part was written, with the state database refusing the `file_log` insert (a full disk) while the chunk's own row still completed, left a failed manifest declaring that chunk. The resume over that manifest adopted the part without checking the ledger, and the finished run declared more parts than the ledger recorded; the rows were delivered, but the ledger the run is graded by was short. **Now** a resume reads a completed chunk again whenever the ledger holds no row, or fewer rows, for the part the manifest declares, whether or not the manifest names it; the old part is left out of the manifest. **Behaviour change:** such a resume exports that chunk once more under a new file name and moves the old part to `_quarantine/<run_id>/` in the destination, so the prefix keeps one file per chunk and the manifest names it; the old part stays recoverable there. State and tables written before the upgrade need no step: only a run that is still unfinished when the new binary resumes it has its ledger repaired this way, and a run that already completed keeps the short ledger it finished with. A leftover part that an earlier resume left in the prefix beside its re-export stays where it is until an unfinished run is resumed on the new binary, which moves every untracked part to `_quarantine/`, or until you delete it by hand; `rivet validate` lists it as an untracked object. Resume after `rivet repair` of a failed run reads the repaired chunk again for the same reason (repair logs its part under its own run id), at the cost of one more file in `_quarantine/`.
