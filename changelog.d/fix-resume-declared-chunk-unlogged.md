- **A resumed range-chunk run finalized a manifest declaring a chunk whose `file_log` row was never written.** A run that failed after a chunk's part was written, with the state database refusing the `file_log` insert (a full disk) while the chunk's own row still completed, left a failed manifest declaring that chunk. The resume over that manifest adopted the part without checking the ledger, and the finished run declared more parts than the ledger recorded; the rows were delivered, but the ledger the run is graded by was short. **Now** a resume reads a completed chunk again whenever the ledger holds no row, or a different row count, for the part the manifest declares, whether or not the manifest names it; the old part is left out of the manifest. **Behaviour change:** such a resume exports that chunk once more under a new file name and moves the old part, when the resume's manifest declared it, to `_quarantine/<run_id>/` in the destination, where it stays recoverable; the new manifest names the re-export. State and tables written before the upgrade need no step: only a run that is still unfinished when the new binary resumes it has its ledger repaired this way, and a run that already completed keeps the short ledger it finished with. This change does not clean the prefix of other leftovers: a part that an earlier resume left beside its re-export, and a part of a chunk the ledger never recorded that the resume's manifest did not declare, stay in the prefix on a resume with no manifest or another run's manifest as they did before; only the resume over the run's own manifest moves untracked parts to `_quarantine/`. Delete such a part by hand; `rivet validate` lists it as an untracked object. Resume after `rivet repair` of a failed run reads the repaired chunk again for the same reason (repair logs its part under its own run id), at the cost of one more file in `_quarantine/` when the manifest declared the repaired part.
