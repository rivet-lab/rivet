- **`rivet load` into BigQuery refuses a part holding a NULL list, before it writes anything.** Behaviour change. Before, a NULL in a PostgreSQL array column (`TEXT[]`, `INTEGER[]`, `DOUBLE PRECISION[]`, `DATE[]`, `TIMESTAMP[]`, `TIMESTAMPTZ[]`, `TIME[]`, `BYTEA[]` and the rest) was loaded as `[]`, because a BigQuery `REPEATED` field cannot be NULL: NULL and an empty array became the same value, silently. **Now** a part whose list column holds a NULL list is refused with `RIVET_LOAD_VALUE_OUT_OF_TARGET_RANGE` (exit 5, a refusal) naming the column; nothing is written, for a full load, an incremental load and a change log alike. An empty array, an array holding NULL elements (BigQuery keeps them as `item` NULL), a column the plan does not declare an array and a change-log delete, whose non-key columns are NULL by construction, load as before. A table loaded before the upgrade is not touched: the `[]` it already holds stays, and no new load of the same data succeeds. **What to do:** for a batch export, in the export's `query:` read the column as `COALESCE(a, '{}') AS a` to load `[]` on purpose, or as `a::text AS a` to keep the NULL in a `STRING` column, or correct the value at the source. A `mode: cdc` export has no `query:`, and the part that holds the NULL stays staged, so fixing the source alone does not lift the refusal on the next load: give every row a list in the source, then re-baseline the stream (the refusal prints the recipe); a `columns:` override does not help, since PostgreSQL does not convert a list to text (`RIVET_SOURCE_OVERRIDE_WIRE_MISMATCH` at the run). The earlier documentation said `columns: {col: string}` keeps the NULL; it does not for an array column. To find the rows an earlier load emptied, compare the table's `[]` rows with the source rows where the array is NULL.
